# Профили CI

База замеров — `main` 440e0ff после PR #58. Исходный [GitHub Actions run 44263517490](https://github.com/Surpd/OGE-bot/actions/runs/44263517490): 1905 passed, pytest 526,70 с (без запуска runner и подготовки зависимостей), workflow от 08:01:52 до 08:11:29 UTC — 577 с. Распределение длительностей pytest показывает стоимость конкретного case, а не всего семейства.

| Сценарий | До | После / измерение |

| Изменение №11, быстрый сигнал | полный pytest, 526,70 с на GitHub | локально 179 passed, 9 deselected, pytest 35,33 с, wall 36,70 с; PostgreSQL 17, параллельный расширенный набор |
| Общее ядро, БД или CI, быстрый сигнал | полный pytest, 526,70 с на GitHub | локально 1766 passed, 144 deselected за 216,30 с с PostgreSQL 17; без установки и runner |
| Только документация | запускался полный pytest/PostgreSQL | классификация и gate без PostgreSQL и pytest; время отдельного GitHub PR не измерено |

Среды разных замеров различаются; эти цифры не являются честным сравнением wall time GitHub до и после. Fast — ранний сигнал, а не разрешение на merge: для программного PR существующий статус `quality` ждёт **fast, full, Docker и, при необходимости, mass**. Полный набор специально сохранён на каждом программном PR, чтобы не ослабить существующую защиту; суммарные вычисления могут увеличиться. Документационным считается только изменение `.md` вне `.github`; любые сомнительные файлы проходят как программные. Чтобы закрепить защиту, в branch protection должен оставаться обязательным статус `quality` (и нельзя заменять его только на `fast`). Настройки GitHub в этом PR не меняются.

## Уровни

- **fast**, каждый программный PR: Ruff, mypy, PostgreSQL 17, общие контракты, сценарный движок, пользовательский №19, статистика, вебхук и тесты изменённых файлов/номеров, исключая явно помеченный `mass`. Тесты 6–18 запускаются через общий UX harness; 1–5 — сценарным контрактом. Изменение неизвестного общего кода, хранилища, политики ответов, миграций, зависимостей или CI выбирает все тесты `not mass` с PostgreSQL. Не найденный base не трактуется как документация.
- **full**, каждый программный PR и push в main, а также ручной `workflow_dispatch` с `profile=full`: Ruff, mypy, **все** тесты без фильтра, PostgreSQL 17, `--durations=50`; Docker-рендер запускается отдельно. Ручной запуск выбирает конкретную ветку/ref и требует её полный `expected_sha`; при несовпадении checkout с ним job завершается ошибкой. На main запуск не отменяется последующими push.
- **mass**, ежедневно по расписанию, при изменении генераторов/математических тестов/инфраструктуры QA и вручную с `profile=mass`: все `@pytest.mark.mass`, включая PostgreSQL-стресс. Все они также остаются в full. При правке генератора требуется и mass job; его статус включён в `quality`. Порогов seed/fingerprint не уменьшали.

Локально, из корня (для PostgreSQL используйте тестовую БД, не production):

```bash
uv sync --frozen --all-extras
uv run ruff check .
uv run mypy app
DATABASE_URL=postgresql://postgres:postgres@localhost:5432/oge_trainer uv run python scripts/ci_select.py fast origin/main
DATABASE_URL=postgresql://postgres:postgres@localhost:5432/oge_trainer uv run pytest -q --durations=50
DATABASE_URL=postgresql://postgres:postgres@localhost:5432/oge_trainer uv run pytest -q -m mass --durations=50
```

`ci_select.py` сравнивает merge-base с `HEAD`; незакоммиченные изменения в diff не входят. Для отдельного номера можно вызвать pytest по его файлам с `-m 'not mass'`, а для приёмки — без этого фильтра. Изменённый `tests/conftest.py` или другой общий fixture всегда даёт широкую регрессию. Если семантическую принадлежность нельзя надёжно вывести из имени, выбирается широкий профиль, а не пустой набор.

## Что перенесено в mass

Отметки применены к самим test functions, без изменения тел и порогов: 300 PNG-вариантов каждой из восьми семей №11; массовые оракулы и разнообразие №7, 9, 10, 12–14 и 19; 250/1200 seed сюжетов ROUTE/TYRES/TARIFF/GARDEN/PAPER/FLAT/STOVE; 300 replay №15 и 50-seed геометрические проверки №17–18; массовый контроль объяснений №18; 10 000 записей истории PostgreSQL. Односеменные регрессии, мутации, проверка реестра, ответов, восстановления и PNG остаются и в fast при выборе номера. Маркер означает классификацию, а не пропуск в full.

Контроль покрытия: 1910 tests collected после добавления пяти проверок классификатора против 1905 в исходном наборе; сравнение node ID: 1905 исходных, 1910 текущих, удалено 0, добавлено 5. Из них 144 помечены mass и 1766 — non-mass; full включает обе группы. В изолированном checkout намеренно включали три дефекта: пустой публичный реестр №19, принятие любого ответа и исключение №15–19 из memory-истории. Соответствующие тесты из fast завершились ошибкой. При эксперименте обнаружен и усилен существующий тест: после первого неверного ответа он теперь проверяет активное состояние и отсутствие зачёта.

`pytest-xdist` не включён: тесты используют PostgreSQL, глобальные реестры/monkeypatch и создание БД; полная изоляция их параллельного исполнения не доказана. Никакие тесты не удалены, массовая компактизация и production-БД не используются. Fast для общих изменений может превысить 120 секунд; выбор ограничен безопасностью, а не фиксированным бюджетом. Изменение workflow или маршрутизатора само запускает расширенный fast, full, Docker и mass.

## Профиль исходного набора

Полный локальный `--durations=50` с PostgreSQL 17: [список всех 50 случаев](../reports/ci-baseline-durations-50.txt), 1905 passed за 628,37 с. Во время него параллельно выполнялись два адресных прогона, поэтому стоимость отдельных случаев приблизительна; GitHub baseline выше — независимый запуск.

- №11: восемь отдельных 300-seed проверок разнообразия и полного PNG/графического oracle — от 12,21 до 22,09 с на семейство. Они проверяют ёмкость и валидность множества, тогда как быстрые случаи сохраняют отдельные фиксированные проверки координат, растровых меток, подмены hash, ответа и replay.
- №1–5: ROUTE 250 seed — 26,74 с; 12 параметров STOVE по 250 вариантов занимали примерно по 7,8–8,0 с; FLAT — 7,07 с, TARIFF — 3,94 с. Повторный общий oracle на разных семействах выглядит похожим, но проверяет разные условия, поэтому тесты не объединены и не удалены.
- №15–19: №18 массовая проверка объяснений — 20,30 с; его 50-seed геометрия и PNG/replay достигают 10,14 с на семейство. №19: 500 seed/покрытие банка 4,10 с, длины утверждений 4,09 с. Геометрические mutation/replay и пиксельные проверки остаются в fast для затронутого номера; массовый повтор рендеринга перемещён в mass.
- PostgreSQL: dispatcher navigation/graphic issuance — 2,74 с, прочие его интеграционные случаи не попали выше в топ-50; 10 000 строк истории относятся к стрессу, но тесты транзакций, конкурентных ответов, миграций и восстановления остаются в расширенном fast и full. Telegram UX: обход всех семейств №16 — 4,61 с, публичных семейств №15 — 4,33 с; это функциональные проверки, а не кандидаты на удаление.
- Даже если похожие проверки модели и PNG частично повторяют вычисления, они защищают разные границы: независимый ответ, наблюдаемый рисунок и сохранённые байты. Они не подменены сравнением renderer с самим собой и остаются в полном CI.
