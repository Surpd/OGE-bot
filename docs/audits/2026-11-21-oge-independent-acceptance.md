# Независимая приёмка банка OGE Bot: требования к следующему аудиту

**Связанный реестр:** [2026-11-21-oge-real-telegram-audit.md](2026-11-21-oge-real-telegram-audit.md).  
**Статус:** план проверки, а не разрешение на реализацию или merge.  
**Контрольная база на 21.11.2026:** main 396b54ba614757b618749e605bc01a2c394cdd27, Render live dep-dc0sb7brjlhs73a9u4e0.

## 1. Принцип: независимое доказательство, а не повторение генератора

Нельзя считать полноценной приёмкой тест, который:
- генерирует условие одним шаблоном и потом сравнивает разбор с таким же шаблоном;
- сверяет PNG с побайтовой копией собственного renderer, но не оценивает масштаб и семантику;
- проверяет совпадение ответа и oracle, но не проверяет, что упражнение требует заявленного навыка;
- генерирует 1000 корректных экземпляров одного типа и объявляет все реальные типы №18 исследованными;
- использует «всё зелёное» как доказательство отсутствия дефектов в Telegram Rich на физическом телефоне;
- объявляет задачу ФИПИ-подобной без ссылки на конкретный исходный тип и его математический инвариант.

Для каждого тестируемого семейства нужны три независимые плоскости: **математика/геометрия**, **педагогическая редактура**, **реальная предъявляемая форма**.

Не требовать от владельца вручную просмотреть тысячу задач. Агент сам строит репрезентативные выборки, выводит аномалии, проверяет их и формирует каталог. Пользователю отдавать выборочный понятный preview лишь для финальной визуальной приёмки.

## 2. Инвентаризация всего покрытия до исправлений

Сформировать машинную таблицу для **№1–25**, где для каждого семейства/подтипа есть:

- ID, номер, статус в production, версия генератора, источник(и), год/атрибуция источника и уровень подтверждения;
- точный математический навык, обязательные и факультативные преобразования, запрещённые вырожденные случаи;
- число математически разных конструкций (не просто разных seed или PNG-хешей);
- структура подсказок и решения, корректность языка и величин;
- профиль Rich/PNG, возможность безопасного fallback и сохранения режима в snapshots;
- наличие исходного чертежа, его смысл, роль condition/solution, контроль того, что не раскрывается готовый ответ;
- текущая полнота относительно реальных каталогов ФИПИ и исторических/учебных банков. Не смешивать «источник найден» с «источник визуально и предметно проверен».

Для №6–19 сверить количество и порядок циклов не только по учебной матрице, но и через реальную транзакционную выдачу. Для №1–5 проверить согласованность одного сюжета на всю пятёрку. Для №20–25 различать источниковые карточки и авторские; проверка письменных решений не должна использовать платный API в рамках данного аудита.

## 3. Массовый математический + редакционный прогон

Для каждого семейства:

1. Подобрать фиксированный набор seed и дополнительный случайный набор, с границами параметров и парами намеренно сложных/простых вариантов. Обязательно включить seed, воспроизводящий наблюдённый дефект, если его можно установить легитимно из истории выдач.
2. Независимо решить условие символически/численно/геометрически. Оракул не должен использовать тот же текстовый шаблон разбора. Для №19 проверять каждое утверждение по теореме или контрпримеру.
3. Проверить педагогический инвариант конкретного прототипа: если задача про общий знаменатель, знаменатели реально требуют преобразования; если про сокращение, есть реальное сокращение; если про график, ответ определяется по видимым свойствам; если про геометрию, все используемые связи следуют из условия, а не из художественного сходства рисунка.
4. Проверить недопустимые/бессмысленные формы, не накладывая запреты глобально: +0, −0, x−0, заранее сокращающиеся одинаковые корни, лишние скобки, нерелевантные дополнительные числа, физически недоопределённые условия, неестественные числительные, внутренняя англоязычная терминология, «просто применяем формулу» без показанного критического шага.
5. Проверить приемлемость числовых параметров как диапазонов реальных прототипов; не запрещать правдоподобные большие числа только на основании вкуса. Например, √4266 в №7 допустим при наличии таблицы квадратов.
6. Отдельно оценить **содержательное различие** примеров: одинаковое вычисление с другими числами не равно новой математической конструкции. Отчёт должен отдельно показывать unique task ID, unique fingerprint, unique mathematical shape и количество разных семейств.
7. Учесть обратные вопросы и форматы ответа (числитель дроби, интервал, множество, номер графика, целое/дробь, несколько цифр), устойчивость проверки к десятичной точке/запятой.

Выход — явная таблица проблемных случаев с **условием, ответом, разбором, семейством, seed, причиной, severity и ссылкой на проверенный исходный прототип**. Если seed из пользовательского скриншота не восстановлен, так и указать; использовать независимый вновь найденный воспроизводимый seed.

## 4. Аудит учебных разборов, а не только результата

Каждая задача должна иметь достаточно объяснения для своего уровня. Не требуется делать трёхстраничное доказательство для Пифагора 16²+30².

Обязательные негативные проверки:
- №11: никогда не выводятся constant, linear, inverse, «контрольные значения соответствуют виду…» без содержательного пояснения. Для разных графиков указаны нужные свойства: k, b, ветви, четверти, y(0), вершина, контрольная точка.
- №12: двоеточие в «Выразим C: C =…» не превращается в математическое деление.
- №13: промежутки, строгие/нестрогие границы, ASCII <=, >= проверены как единая математическая композиция.
- №14: склонение количеств и явная подстановка в формулы прогрессий; точный смысл «тормозного пути» и превращения A в Б.
- №15: корректный индекс S с MBN, шаг обоснования подобия, неразорванные перечисления и пунктуация.
- №16: переход tg=7/24 → sin=7/25 в ромбе объяснён, а не просто постулирован; короткие задачи не раздуваются.
- №18: для составных фигур показывается именно школьное разбиение/достраивание, а не только ответ координатной формулы.
- №19: у истинного утверждения — применимое свойство, у ложного — корректный контрпример; не использовать круговую «проверку», повторяющую эталонный текст.

Утверждение «разбор совпал с ожидаемым строковым шаблоном» не засчитывать как педагогическую проверку.

## 5. Сквозной тест математического представления

Проверить **условие → подсказка 1/2 → разбор → результат → история → восстановление** для семейства на одной и той же математической модели.

Контроль:
- Rich предпочтителен для поддерживаемой нотации; принудительный PNG только с точной документированной причиной;
- не должно быть случайного переключения Rich/PNG для разных seed одного типа, не обусловленного явным пользовательским режимом или подтверждённой несовместимостью Telegram;
- формула не меняет семантику при разметке: разделители текста, «:», минусы, степени с отрицательным показателем, дроби, смешанные числа, корни, индексы, sin/cos/tg, системы и интервалы;
- не показывать в ученическом тексте сырые TeX-команды, незавершённые формулы, латинские внутренние kind-tags, S_MBN, одиночные «1.» и оторвавшиеся точки;
- локализация вывода: десятичная запятая в русских математических строках, при сохранении совместимого парсера ответов с точкой;
- при явном отказе Rich от Telegram резерв PNG работает **однократно и детерминированно**, без двойной отправки после неопределённого состояния сети; сохранённый профиль действителен после перезапуска;
- качество реального клиента нельзя доказать только HTTP-успехом sendRichMessage: это отдельная ограниченная визуальная проверка.

## 6. Проверка иллюстраций

**Сначала** геометрическая модель независимо подтверждается: положение меток и отрезков, биссектрисы, средние линии, высоты, касательные, пересечения, параллельность, инварианты длин и углов, совпадение с условием и источником. **Затем** пиксели.

Для каждого семейства визуально анализировать набор сцен, а не одну картинку: обычную, экстремальную, плотную (много меток), близкие точки, большой/малый коэффициент. Рендер 360/390/430 px + сравнительный предварительный просмотр в реальном Telegram для репрезентативных исключений.

Особые правила:
- №7: не пиксельный шрифт 5×7 для подписей; масштаб и позиции читаются.
- №11: три графика крупнее внутри полезной ширины, единичные метки различимы, контрольные точки у гипербол доступны для сравнения коэффициентов.
- №13: на графических альтернативах нельзя считать две граничные точки видимыми, если их кольца перекрываются. Не спасает только разнесение цифр.
- №15–17: рисунки не обязаны быть «в масштабе», но не могут противоречить условиям; подписи не налезают, расстояния/углы не обозначены заведомо ложно.
- №18: проверка клеток по пикселям и координатам; при сложной площади отмеченные вспомогательные фигуры выводятся **в разборе**, не в условии.
- №22: готовый построенный график в ответе не показывать в condition, если построение — само задание. Для №23–25 чертёж исходных данных может и должен присутствовать, когда он требуется условием.

Отчёт обязан различать **валидный PNG** и **хороший учебный чертёж**.

## 7. Навигация, Mix, выдача и история

Проверить транзакционно в PostgreSQL 17 и через Telegram-dispatch, включая повтор webhook, возвращение из старого сообщения и перезапуск процесса.

- №17: /start → «По номеру» → №17 → сохранённая практика → «Продолжить»; отдельно «Начать заново», «Выбрать тип». **Актуальная** кнопка обязана работать; **старая** обязана отклоняться без изменения состояния. Зафиксировать текущий screen, message_id, revision и момент сохранения, без публикации персонального user_id.
- Для всех №6–19: «Все типы» расходует переставленную очередь; за полный цикл показываются все **доступные** семейства, нет двух последовательных одинаковых узких конструкций при наличии альтернатив, после перезапуска остаток сохраняется; ручной выбор конкретного типа не подменяется другим.
- Для №1–5: смешанный и отдельный режим учитывают один общий сюжет и историю уже показанных конкретных условий.
- №18: при исчерпании конечных fingerprint корректный новый цикл, без зависаний; проверять реальные математические shapes, не hash PNG.
- №19: короткая серия не должна систематически повторять «два верных»; отдельно исследовать 1/2 правильных и возможную учебную опцию «выберите неверные», включая смену семантики маски ответа. Утверждать, что такая формулировка соответствует экзамену-2027, только после подтверждения первоисточника.
- №20–25: различать продолжение, новый случайный, пропуск, завершённое, просмотренный разбор, graded, ошибку, повтор; до исчерпания подтипа не возвращать тихо уже просмотренное.
- Проверять сохранение уже решённых задач, истории и правильность восстановления старых snapshots; не хранить PNG отдельными пачками в базе без необходимости.

## 8. Отдельное расширенное исследование №18

Самостоятельно изучить открытый банк ФИПИ, демоверсии, проверенные каталоги №18 и рисунки оригиналов. Нельзя делать только текстовый поиск: геометрия типа часто содержится в рисунке.

**Первый подтверждённый пробел:** https://math-oge.sdamgia.ru/problem?id=323790 — произвольная закрашенная фигура на клетчатой сетке, площадь через охватывающий квадрат и вычитание лишних частей / альтернативно формулу Пика.

Разделить конструкции минимум по математическому навыку:
- произвольный выпуклый многоугольник через вычитание внешних треугольников;
- невыпуклая/составная фигура через разбиение или вычитание;
- наклонные многоугольники, для которых нельзя непосредственно считать стандартные высоты;
- разные способы посчитать площадь одной фигуры, включая формулу Пика **только как дополнительный способ**, если она подходит, а не замену школьного разбора;
- прочие реально подтверждённые подтипы №18: окружности, отношение площадей, отрезки на сетке, сравнение длины; включать лишь при наличии доказанного источника именно для задания 18.

Для каждого нового семейства требуется минимум один реальный первичный прототип с точным изображением, воспроизводимая координатная модель, независимый oracle, учебные подсказки и решение с дополнительным рисунком, проверка сложности и локализации, массовый прогон и сохранение snapshots.

**Не придумывать квоту «добавить минимум 10»:** число расширений определяется источниками и независимым качеством, а не косметическим увеличением счётчика.

## 9. №19: исследование формулировок и совместимости

Базовый банк содержит 172 утверждения. Не нужно генерировать новые факты без проверки и пересмотра ключей.

- Реально реализовано: одно/два верных из трёх (seed-паритет), вопрос всегда «Какие ... верны?».
- Проверить действующие формулировки в демоверсиях ФИПИ отдельно для каждого года/версии. Учебное «Выберите неверные» возможно как **дополнительный режим**, но не маркировать как подтверждённый формат действующего экзамена без первоисточника.
- Разработать, если согласовано позже, независимый вопрос kind: find_true/find_false, target_count, answer_mask, versioned parse; проверить комплементарность маски без ошибочных ответов на старые задания.
- Балансировать длину ответа и позиции по коротким сериям, а не полагаться на паритет криптографического seed; не ухудшать разнообразие математических тем.
- Не заменять исторические snapshots и не пересоздавать уже выданные попытки.

## 10. Артефакты самостоятельной приёмки

До просьбы к пользователю «посмотри ещё 500 фото» агент должен представить:

1. **Матрицу покрытия №1–25**: все семейства, source verified / only catalog / author, число реальных конструкций, проверяемые навыки, текущая включённость, количество уникальных примеров и пробелы.
2. **Реестр дефектов** со строгими статусами: reproduced / fixed-and-regressed / not-reproduced / requires-clarification / accepted-as-valid. У каждого дефекта конкретный образец, семейство, seed или прямое указание, почему seed неизвестен, исходный текст, фактическая формула и безопасный способ проверки.
3. **Галерею учебных примеров**: разнообразные типы и экстремумы параметров, **условие вместе с разбором**, а не только PNG чертежа; сравнительные mobile previews и отметки об опасных формулах.
4. **Отчёты по ротации** №6–19, отдельно выбранный тип, Mix, первая полная очередь, исчерпание, restart и сохранение истории.
5. **Независимую сверку реальных прототипов** по №18 и слабым/новым типам остальных номеров. Неподтверждённые идеи не переводить в production молча.
6. **Диагностику Telegram/навигации №17**, включая доказательство, как отличить ожидаемое отклонение старой кнопки от ложного отказа актуальной.
7. **Прозрачную границу автоматической приёмки:** что реально протестировано на настоящем Telegram iPhone, что проверено только на модельном API, а что требует финального короткого user smoke.

## 11. Границы безопасной работы

- Этот документ не является разрешением менять код или алгоритмы проверок. Следующим шагом пользователь отдельно утвердит имплементационный промпт.
- Никаких автоматических merge, деплоев, боевого создания новых выдач для пользователя, платных OpenAI API-проверок письменных решений или сброса сессий.
- Не публиковать персональные скриншоты/ID в репозитории.
- При будущих исправлениях: только новые версионированные задачи и логика выдачи, сохранение уже выданных snapshot, результата и истории. Стараться исправлять предъявление старых задач без изменения их математической модели.
- Итоговая приёмка должна фиксировать **почему найденные пользователем проблемы не были пойманы предыдущими 2165 тестами**, какие независимые новые проверки это меняют, и как проверяется отсутствие новых побочных эффектов.

**Критерий успеха:** после самостоятельного аудита агент показывает конкретные проблемные конструкции, их первопричины, корректные исправления и доказательства регрессии. Пользователь должен просмотреть несколько репрезентативных исключений на телефоне, а не вручную инспектировать каждое семейство.
