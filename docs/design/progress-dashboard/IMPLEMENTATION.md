# Задание Codex — внедрить новый PNG «Твой прогресс»

**Эта ветка содержит только референсы и план.** В отдельном implementation-PR обновить интерфейс, ничего не сливать/деплоить автоматически.

## Где смотреть существующую реализацию

- app/bot/progress_image.py: действующий Pillow-рендер, render_overview, render_progress_image, dashboard_tile_values, dashboard_tile_accent, send_progress_image, edit_media, асинхронный вызов через asyncio.to_thread, PHOTO_LIMIT и текстовый fallback.
- app/bot/progress.py: progress_navigation и progress_keyboard, callbacks refresh, history, errors, details, return.
- app/persistence/training_insights.py: источник истины для статистики, success_rate, success_label, MIN_ANSWERED_SAMPLE = 5, NUMBERS = 1–19.
- tests/test_progress_image.py и tests/test_training_insights.py: существующие регрессии.
- AGENTS.md, specs/TRAINING_UX_CONTRACT.md, specs/TRAINING_ARCHITECTURE.md, specs/LESSONS_LEARNED.md: обязательные инструкции. Учесть LL-12, LL-19, LL-20, LL-21 и LL-22.
- README.md и reference_renderer.py в этом каталоге: утверждённая геометрия, цвета, размер и демонстрация.

## Задача по шагам

1. **Ограничить изменение представлением.** Перестроить render_overview в app/bot/progress_image.py, заменить прежние три столбца и высокие белые карточки на пять компактных столбцов одинаковых ячеек. Сохранить render_progress_image и send_progress_image, существующие кнопки, защиту revisions, refresh/edit_media, удаление устаревшего сообщения и fallback в текст. Никакой новой БД, роутов или платного сервиса.
2. **Взять штатные числовые значения.** Для каждого номера брать insights['numbers'][number]['correct'] и ['answered_tasks']; процент — через success_rate/success_label, не через количество сообщений или попыток. Общие metrics брать из insights['total']: correct, skipped и success_rate. Не изменять функции агрегации, историю и рекомендации.
3. **Реализовать одну плитку.** Номер сверху слева, correct/answered_tasks снизу слева, процент (или длинное тире) в постоянной правой зоне. Для пустых 0/0 — тире, не 0%. Положение, высота, ширина, шрифтовая иерархия одинаковы при пустых, плохих, хороших и больших результатах. Подгонка по ширине не должна сдвигать соседние ячейки.
4. **Цвет без подмены педагогического смысла.** Для процента плавно интерполировать красный → янтарный → зелёный. Отдельно держать проверку answered_tasks >= MIN_ANSWERED_SAMPLE: до пяти процент предварительный, номер не получает подтверждённый статус освоения. Можно применять мягкую цветную подложку для предварительного процента, как в референсе. Не менять семантику существующего dashboard_tile_accent молча: при необходимости разделить цвет процента и цвет оценки номера. Внизу коротко обозначить порог из пяти ответов.
5. **Шапка пользователя.** Короткая строка с доступным именем и при наличии username, ниже только «Твой прогресс». Не дублировать имя и не показывать персональные ID. Из callback не получать имя через message.from_user без проверки: это может быть сообщение бота. Передать данные пользователя явно из Telegram event или уже доступного профиля; при отсутствии имени fallback без вымышленного аккаунта. Аватарку по сети не загружать.
6. **Сейчас 19, дальше 25.** Количество плиток задаёт параметр или серверная конфигурация поддерживаемых номеров. На текущем этапе прогресс и навигация ограничены №1–19, будущая ёмкость — №1–25 с пятью строками. Сценарий с 25 в preview является будущим, не заявлением о поддержке №20–25. Не включать №20–25 в пользовательское меню до их действительного выпуска.
7. **Сохранить способ отправки.** Рисовать PNG локально Pillow, в памяти BytesIO; в Telegram отправлять BufferedInputFile. Сохранить asyncio.to_thread, ограничение размера Telegram photo, обработку невозможности отправки и возврат к тексту. Не складывать картинки на Render disk или Supabase Storage. Не добавлять новые шрифтовые файлы: в Docker уже установлены DejaVu, в приложении есть matplotlib. У прототипа может использоваться Inter на компьютере разработчика, это не production-требование.

## Приёмка

- Референсы 19 и 25 номеров в одной системе, без изменений геометрии плитки в зависимости от наличия процентов; контрольные PNG и скриншоты мобильного просмотра (360/390 px).
- Проверки случаев: пустая статистика; 1/1, 4/4 (предварительные), 5/5, 0/5, 2/5, 4/5, 1/2, 2/3, 0/0; большие значения счётчиков; длинное имя и username; отсутствующий username; общий 0/0; 19 и 25 плиток.
- Без потерь: total.correct, total.answered_tasks, total.success_rate, total.skipped и по-номерные correct/answered_tasks совпадают со старым экраном; пропуск не создаёт answered task.
- Нулевая выборка даёт «—», округление согласовано со штатным success_label; не смешивать число принятых попыток и число задач с ответом.
- Цикл Telegram: открыть, обновить, вернуться из истории/ошибок, текстовый fallback при сбое PNG; актуальные и устаревшие callback остаются защищены; никакие кнопки статистики не изменяют прогресс.
- Адресные tests/test_progress_image.py, tests/test_training_insights.py и python scripts/check.py progress; затем полный Ruff, mypy, pytest c PostgreSQL 17 и Docker build. Реальный Telegram-smoke-test отмечать отдельно, а не выдавать имитацию за проверку.
- Выполнить внедрение в **отдельном PR**, без merge, deploy и операций с production-данными. Отчёт: SHA, ссылка на PR, контрольные PNG/скриншоты, статус CI и известные ограничения.

## Особенности визуального кода

reference_renderer.py — воспроизводимый **дизайн-прототип**, не готовая замена. Его per_task — словарь {номер: (correct, answered_tasks)}, а источник production — training_insights. У прототипа правый процент цветной даже на маленькой выборке, но номер остаётся нейтральным до пяти ответов. Так отображается направление цвета без преждевременной педагогической оценки. При любом конфликте с нормативным UX-контрактом сохранять смысл статистики.
