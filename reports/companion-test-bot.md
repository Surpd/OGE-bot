# Второй Telegram-бот в существующем oge-trainer

Команда `/start` открывает [bop Admin](../specs/ADMIN_ANALYTICS.md). Точные проверки доступны в разделе «Инструменты» и через `/qa`.

Кандидат от `main` `50b192e`. Отдельный draft PR; никаких действий в Render,
секретах или production не выполнено. Два Telegram-клиента работают в одном
процессе, на одном SHA. Второго сервиса, новой БД, workspace или Mini App нет.

## Что Дмитрий получает

После Start — четыре короткие проверки: печи 23/12/20, известный дефект №16,
сложная формула Rich/PNG, фото №20 с явной имитацией. Дальше всё кнопками:

- «По номеру / типу»: №1–5 по публичному сюжету и позиции, №6–19 по включённому
  семейству, №20–25 по проверенной карточке банка. Для комплекта №1–5 все пять
  позиций доступны прямо под карточкой с тем же исходным снимком.
- «Найти карточку / ID»: короткий QA ID, полный ID банка или его числовая часть
  (например, `438301`). «Недавние точные карточки» возвращает последние 12 снимков.
  В «Истории тестов» доступны только собственные попытки во втором боте.
- Seed + версия вводятся после выбора типа. Если версия не поддерживается,
  снимок вытеснен из 12 последних или идентификатор неоднозначен, бот отказывает
  явно. Похожая задача не подставляется. Для №19 необходим snapshot: одного seed
  недостаточно для восстановления зависимого от истории планировщика.
- «Повторить этот вариант», «Повтор ошибки», подсказка, разбор, Rich/PNG,
  «Следующая проверка», «Диагностика». Диагностику можно скопировать целиком:
  номер, семейство, версия, seed/ID, последний шаг, SHA, режим доставки.
  В ней нет owner ID, токенов, фотографий или ученической истории.
- «Как ученик» — тот же обычный router, навигация, выдача, подсказки, ответы,
  сохранение и продолжение. Отдельная кнопка под вводом «🔬 Проверки» возвращает
  в инструменты; активная тестовая тренировка сохраняется. Обычный бот такого
  меню не получает. Сброс с подтверждением удаляет только тренировку текущего
  тестового владельца; последние точные снимки остаются для воспроизведения.

Это не обещание покрытия всех возможных экзаменационных конструкций:
выключенные семейства не включаются автоматически. Каталог использует те же
публичные реестры, генераторы и проверенные банковские карточки, что приложение.

## Изоляция и lifecycle

Основной `/telegram/webhook`, bot session, repository и health остаются прежними.
Отсутствующий второй токен выключает companion. Неверный токен, совпадающая bot
identity, пустой/невалидный owner allowlist, ошибка getMe/setWebhook, отсутствие
прав на схему или недоступная БД выключают только companion. Он запускается
фоновой задачей после подготовки основного; ожидание Telegram ограничено.
На shutdown закрывается только его клиент и pool, deleteWebhook не вызывается.

Второй webhook — `${WEBHOOK_BASE_URL}/telegram/test-webhook`. Случайный секрет
генерируется автоматически, сохраняется в закрытой `companion_identity` и
переживает restart; он не совпадает с основным. В getMe проверяется фактический
bot ID. Проверяются secret, owner, private chat, отсутствие forwarding/inline и
принадлежность сообщения callback второму боту до чтения тренировок. Дедупликация
update_id отдельная; неопределённая доставка не повторяется автоматически.

В той же БД автоматически создаётся `oge_test_bot_<test_bot_id>`. Отдельный pool
(до 3 соединений) имеет только эту схему в search_path; public/$user не добавляются.
Схема без маркера или совпадающая с основным default search_path отвергается.
Публичным ролям отозван доступ; RLS включён. Туда применяются общие миграции и
импорт статического банка из репозитория, без копирования production данных.
Схема нужна для настоящего ученического flow и exact rerun после restart.
Это изоляция на уровне приложения/namespace, не отдельный DB credential или
отдельная аппаратная нагрузка. Обе bot identity разделяют ресурсы одного процесса.

Настройки paid grading переопределяются через ContextVar только на время test
update, ключ модели очищается. Создание model client также запрещено в этом
контексте даже с переданными вручную production settings. /api_test и его старые
callbacks блокируются. Вне этого контекста поведение основного клиента прежнее.

## Внедрение после отдельного разрешения

1. Проверить зелёный **полный CI на SHA этого PR**, включая PostgreSQL17 и Docker.
   В существующем Render `oge-trainer` выбрать разрешённую ревизию кандидата
   (Deploy specific commit / соответствующая ветка). Не создавать второй сервис.
   Один процесс означает один SHA у обоих ботов: нельзя запустить другой кандидат
   только для второго токена, оставив первый на иной версии кода.
2. Дмитрий создаёт нового бота у @BotFather. В Environment **существующего**
   `oge-trainer` лично добавляет два значения:
   - `TELEGRAM_TEST_BOT_TOKEN` — новый секрет BotFather;
   - `TELEGRAM_TEST_OWNER_IDS` — собственный числовой Telegram user ID
     (или до пяти явно разрешённых ID через запятую).
   ID владельца не выводится из токена и не назначается первому посетителю: это
   отдельная граница доступа. Секрет не передавать в чат/PR/логи.
3. `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET`, `DATABASE_URL`, `APP_ENV`,
   настройки модели и текущий `WEBHOOK_BASE_URL` оставить прежними. Новый URL,
   schema name, bot ID и webhook secret вручную не настраиваются. Текущая DB role
   должна иметь CREATE SCHEMA; при отсутствии прав companion останется выключен,
   основной бот продолжит работу. Новые привилегии этот PR не назначает.
4. После разрешённого deploy проверить Live SHA в Render, `/health` = ok,
   основной бот и запись `companion_ready` без секретов. Второй бот может
   подготовиться позже основного, в пределах двух минут. При
   `companion_unavailable type=...` он закрыт; исправить только test env или
   разрешённую причину доступа, затем перезапустить. Автоматического платного
   вызова, ручного SQL bootstrap или копирования ученической БД нет.
5. Нажать Start у **нового** бота. Сверить SHA в приветствии/диагностике с Live SHA
   и CI. `RENDER_GIT_COMMIT` берётся автоматически; для локального контейнера
   можно задать `APP_BUILD_SHA` из `git rev-parse HEAD`. Неизвестный SHA так и
   обозначается; это не подтверждение кандидата.

Текущий PR ничего не выкладывает и не меняет в Render. Токен/owner ID и разрешение
на выкладку остаются действиями владельца. Все остальные настройки выполняет код.

## Приёмка с телефона за 3–5 минут

1. **Печи** → каталог виден до условия с 23/12/20 → «№2 этого комплекта» → №1 →
   «Повторить этот вариант». Проверить, что ID/вариант тот же; подсказку и разбор.
2. **Следующая проверка** → №16: увидеть предупреждение об известном дефекте и 90°.
   Оставить красным независимо от того, принят ли ответ 90.
3. **Следующая проверка** → формула: Rich/авто → PNG → повтор. Проверить скобки,
   дробь/радикал и читаемость. «Диагностика» даёт копируемое описание проблемы.
4. **Следующая проверка** → фото: отправить одно фото тестового листа Reply на
   условие → имитировать ошибку → результат → убрать фото. Везде видна имитация;
   это UX/delivery тест, не проверка качества модели. Никаких ученических фото.
5. **Как ученик** → по номеру → одна обычная задача → «🔬 Проверки» → найти 438301
   или открыть недавний snapshot. Снова «Как ученик»: задача/попытки сохраняются.
   Проверить старую кнопку и вход неразрешённого аккаунта: действия не принимаются.

## Rollback

Удалить/очистить только `TELEGRAM_TEST_BOT_TOKEN` в Environment и применить
разрешённый restart/deploy. Второй endpoint отвечает 403, основной сохраняет свой
webhook и токен. Тестовая схема остаётся для exact rerun, автоматического DROP нет.
Для отката всего кода — обычный разрешённый rollback существующего сервиса на
предыдущий SHA; token второго бота предварительно отключить. Не менять основной
webhook вручную. Схему можно удалить отдельно только явным согласованным действием.

## Локальная приёмка в Telegram

Для живой проверки кандидата можно запустить только companion через polling.
Запуск рассчитан на отдельного тестового бота без активного webhook и на
отдельную пустую PostgreSQL 17 на loopback. Остановка выполняется Ctrl+C.

1. Открой чистый checkout SHA из PR №110 и установи зависимости
   командой `uv sync --frozen --all-extras`.
2. В локальном PostgreSQL создай пустую базу `oge_companion_qa`. Можно добавить
   суффикс, например `oge_companion_qa_pr110`. Подключение должно использовать
   `127.0.0.1` или `::1`. У роли должны быть права на создание схемы в этой базе.
3. Для запуска нужны числовой ID основного бота, ID отдельного тестового бота и
   Telegram ID одного–пяти участников приёмки. Подставь свои ID вместо чисел в команде.

   ```powershell
   uv run python -m scripts.companion_polling --primary-bot-id 100001 --companion-bot-id 100002 --owners 123456789
   ```

   Введи URL локальной базы и токен тестового бота в скрытых приглашениях
   терминала. Скрипт проверяет чистоту checkout и выводит запущенный SHA. Если на
   тестовом боте уже есть webhook, используй отдельного бота для polling.
4. По строке `Companion ready` сверь SHA с PR. Открой личный чат с тестовым
   ботом, отправь `/qa` и выбери «Как ученик». Проверь советы в прогрессе,
   разделе тренировок и итогах, смешанный режим и выдачу нового варианта после
   разбора. Сохрани реальные скриншоты выбранных экранов, скрыв личные данные.
   Останови процесс после приёмки.

Запуск читает только выданный ему тестовый токен. Он проверяет ID ботов,
отклоняет URL со внешним адресом или параметрами подключения, проверяет
отсутствие таблицы основного бота в `public` и создаёт изолированную схему
companion. Участники приёмки ограничены списком и личными чатами. Проверка
письменной части в companion использует тестовый режим без вызовов модели.
