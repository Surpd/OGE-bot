# Единый staging-кандидат: исправленные материалы и точный QA

Ветка `staging/qa-materials-candidate` объединяет **ровно** два исходных кандидата:

- #106: `b8006c930c4121f6bf2f6b13bdfab3403b7740a1`;
- #107: `6ded991e415bb66a0ac48a3514d4a6e077f40e4d`.

Оба коммита входят в ancestry ветки. Исходные ветки, Draft PR и main не изменяются.
Предварительный merge в main **не требуется**. Это ветка только для отдельного
тестового бота; production merge/deploy и создание инфраструктуры не выполнялись.

В `CHANGELOG.md` оставлены обе записи. В `error_replay._render` данные #106
отправляются до вопроса, а `controls` #107 заменяет только клавиатуру QA.
У обычного ученика остаётся штатная клавиатура с «Схема / данные». При недоставленных
обязательных материалах условие не выдаётся; QA повторяет тот же snapshot через
«Проверки → Последний точный вариант». Уведомление STOVE обновлено: #106 уже включён.
Сами snapshots, ответы, рисунки и генераторы четырёх стартовых примеров не изменены.

## Один checklist для запуска и живой проверки

1. Взять **итоговый 40-значный SHA из передачи вместе с зелёным CI** этой ветки.
   Не использовать SHA одного исходного PR, плавающий main или latest commit другого
   сервиса. Для локальной подготовки: `git switch --detach <итоговый-SHA>`.
2. Дмитрий создаёт **нового** бота в @BotFather и сам добавляет его Telegram-токен
   только в секреты отдельного staging-сервиса. Здесь никакие сервисы, базы,
   webhook или секреты не создавались и не менялись. Подготовить отдельно разрешённые
   бесплатные Web Service и **пустую отдельную PostgreSQL БД с отдельным пользователем**;
   не использовать production URL, схему существующей ученической базы или её копию.
3. Заполнить [пример настроек](../deploy/staging.env.example): `APP_ENV=staging`,
   один `STAGING_OWNER_ID`, разные ID staging/production ботов, разные staging/production
   hostname, новый webhook secret, `DATABASE_URL` тестовой БД,
   `STAGING_RELEASE_SHA=<итоговый-SHA>`, `OGE_PART2_ENABLED=true`,
   `OGE_GRADING_ENABLED=false`. `OPENAI_API_KEY` должен **отсутствовать**.
   Токен нового бота создаёт и вносит только Дмитрий; в чат его присылать не нужно.
4. Из checkout этого SHA с секретами только в окружении один раз выполнить:

   ```sh
   uv sync --frozen --all-extras
   STAGING_INIT_EMPTY_DATABASE=yes uv run python -m scripts.init_staging
   ```

   Скрипт отказывает для непустой базы и не удаляет данные. Повторный init для следующих
   кандидатов не нужен. Не сохранять `STAGING_INIT_EMPTY_DATABASE` в сервисе.
5. В **новом staging-сервисе** отключить auto-deploy и выбрать Manual Deploy →
   Deploy a specific commit → итоговый SHA. Render передаёт `RENDER_GIT_COMMIT`;
   startup сверяет его с `STAGING_RELEASE_SHA`. Для собственного Docker build из
   этого checkout использовать `--build-arg SOURCE_COMMIT=<тот же SHA>`.
   Сохраняются проверки токена, отдельного origin, маркера БД и отсутствие ключа
   модели **до миграций и регистрации webhook**. Подробнее о разовой подготовке:
   [инструкция окружения](staging-qa.md#один-раз-настроить-владельцу).
6. Открыть нового бота разрешённым аккаунтом; сверить показанный SHA. За 3–5 минут:
   - **Печи 23 / 12 / 20:** каталог печей должен прийти **до** условия. Открыть
     подсказку, разбор и «Повторить этот вариант»: данные и условие те же. Это
     эквивалент скриншота с подтверждёнными границами, не обещание идентичного помещения.
   - **Следующая проверка → №16:** OGE16-D01 seed 19 с углом 90° остаётся
     **известным красным кейсом**. Генератор не исправлен; совпавший ответ не даёт приёмку.
   - **Следующая проверка → формулы:** сравнить Rich/авто и PNG для
     `1280/(4·√(10))²`, затем разбор и повтор ошибки.
   - **Следующая проверка → №20:** своё синтетическое фото Reply к условию,
     «Имитировать результат» и «Имитировать ошибку». Надпись «ИМИТАЦИЯ» обязательна;
     это не проверка точности модели, нет внешнего вызова и расходов.
   - **Выйти:** пройти обычное меню ученика, открыть №1–5 и обычную письменную
     тренировку. Обычный фото-поток сохраняет привязку/удаление, оценка на staging
     остаётся заглушкой. Из меню команд «Проверки» вернуться к точным карточкам.
7. Записать итог мобильного smoke с этим SHA: каталог до условия, точный повтор,
   читаемость формул, явно обозначенная имитация, выход к ученику. Не считать
   автотесты TelegramSession скриншотами телефона. №16 оставить красным независимо
   от остальных результатов. После смены SHA требуется проверка нового кандидата.

## Проверки стыка

`tests/test_staging_materials_candidate.py` проверяет реальный dispatcher staging:
байты нужного каталога перед точным условием 23/12/20, сохранение QA-кнопок,
отклонение старой клавиатуры, запрет выдачи вопроса при сбое материала и явный retry
того же snapshot. Существующие suites #106/#107 проверяют остальные пути, обычного
ученика, входы, фото-заглушку, model kill switch и отсутствие записей QA в обычных
таблицах на изолированном PostgreSQL 17. Полный CI запускается на итоговом SHA ветки.
