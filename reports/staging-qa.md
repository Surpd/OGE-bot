# Отдельный тестовый Telegram-бот: запуск и приёмка

Реализация по изменённому решению Дмитрия: отдельный staging-бот, тот же репозиторий
и кандидат кода. В production режим не включается. Сервисы, боты и базы этим PR
не созданы; токены не запрашивались, production не читался и не изменялся.

## Что уже было и что переиспользовано

- `/api_status` — диагностика модели; `/api_test` — платный подтверждаемый тест.
  Они не являлись owner allowlist и не подходят для безопасного QA. На staging
  обе команды перехватываются, клиент модели дополнительно запрещён в `open_client`.
- Реестр `TRAININGS`, `rotation_history.enabled`, публичный `public_registry` и
  проверенный статический банк определяют каталог. ROUTE не включён.
- `load_original_source` восстанавливает свою выданную задачу, проверяет владельца,
  версии, целостность снимка и графику. Его ограничения сохранены: когда точного
  восстановления нет, показываем отказ, без похожего задания.
- `error_replay._render`, `task_view`, `presentation` показывают №1–19; `card_message`
  и `statement_text` — №20–25. Изменение общего replay — только необязательная
  клавиатура. Машина двух попыток, форматы ответов, подсказки и разбор взяты из
  `ErrorReplayRepository`/`_accepts`, подключённых к отдельному MemoryRepository.
- Обычный режим ученика идёт через прежний dispatcher, генераторы, сессии, фото и UX.
  QA хранит снимки/попытки только в `staging.qa_sessions`; обычные таблицы не пишет.
  Выход восстанавливает прежнюю ученическую тренировку обычной функцией Continue.

## Один раз настроить владельцу

1. Создать **нового** бота через @BotFather. Токен вписать только в секреты нового
   сервиса, не присылать в чат. Сохранить числовые ID нового и рабочего ботов;
   числовой ID — несекретная часть до двоеточия токена, сам токен не копировать в логи.
   Нужен также свой числовой Telegram user ID.
2. Создать отдельно разрешённые бесплатные ресурсы: новый Web Service и **пустую
   отдельную PostgreSQL БД с отдельной учётной записью**. Не использовать production
   URL, копию базы учеников, общую схему Supabase или фотографии учеников.
   Если бесплатный ресурс недоступен, остановиться и выбрать допустимый локальный
   вариант; этот PR не заказывает платный тариф. Создание ресурса — отдельное действие владельца.
3. Выбрать кандидат: полный SHA Draft PR, а после интеграции #106 — SHA объединённого
   кандидата с зелёным CI. В новом сервисе выключить auto-deploy и выбрать этот exact
   commit (Render: Manual Deploy → Deploy a specific commit), а не плавающий `main`.
   До первой попытки запуска заполнить **все** поля из
   [`deploy/staging.env.example`](../deploy/staging.env.example). Новый HTTPS hostname
   доступен после создания сервиса. Production hostname и bot ID нужны для сравнения,
   production токен/ключ/URL БД здесь не требуются.
4. `OPENAI_API_KEY` удалить из окружения staging полностью. `OGE_GRADING_ENABLED=false`.
   Даже случайно добавленный ключ блокирует запуск; `open_client` запрещает внешний
   API независимо от флагов. Создать новый webhook secret, не переиспользовать рабочий.
5. В локальном checkout **этого SHA** с секретами только в окружении выполнить:

   ```sh
   uv sync --frozen --all-extras
   STAGING_INIT_EMPTY_DATABASE=yes uv run python -m scripts.init_staging
   ```

   Это одноразовая инициализация БД, не запуск Telegram. Скрипт откажет, если БД уже
   содержит пользовательские таблицы, представления или sequence. Он не удаляет
   данные. Записывает маркер bot ID / owner / hostname / database / role и QA-таблицу.
   **Не оставлять** `STAGING_INIT_EMPTY_DATABASE` в окружении постоянно.
6. Запустить новый сервис на выбранном SHA. Render автоматически передаёт
   `RENDER_GIT_COMMIT`; он должен совпасть с `STAGING_RELEASE_SHA`. Для собственного
   Docker build из checkout этого SHA:

   ```sh
   docker build --build-arg SOURCE_COMMIT="$STAGING_RELEASE_SHA" -t oge-staging-candidate .
   ```

   Образ сам запускает обычный `app.main:app`; передать ему staging environment
   безопасным механизмом секретов, отдельный URL и доступ к тестовой БД. Не менять
   environment/образ рабочего сервиса. Startup **до миграций и webhook** проверяет
   маркер БД, ID токена, отдельный hostname, SHA и отсутствие ключа модели.
   При успешном старте применяет обычные миграции, импортирует статический банк,
   регистрирует webhook нового бота и меню команд «Обычное меню ученика» / «Проверки».
7. Открыть **нового** бота со своего разрешённого аккаунта, нажать Start. Сверить
   показанный SHA с кандидатом. Другие пользователи, группы, inline/пересланные
   кнопки не получают доступ. Настройка доступа в рабочем сервисе не нужна.

Один SHA может пройти проверку, а другой — нет. Перед следующим кандидатом заменить
`STAGING_RELEASE_SHA` и развернуть именно его; базу повторно не инициализировать.
Старые QA snapshots сохраняются, генерация seed+version отвергает неподдерживаемую
версию. Если нужно испытать исключительно новые данные — использовать новый пустой
тестовый экземпляр, а не очищать рабочую БД.

## Дмитрию: проверка за 3–5 минут

1. **Печи · 23 / 12 / 20**: таблица с диапазонами перед условием; «Подсказка»,
   «Разбор», «Повторить этот вариант». Это seed 155, версия stove-v1.4 — эквивалент
   граничных значений скриншота. Исходный seed скриншота неизвестен, идентичность
   помещения не обещается. До #106 это намеренно красная приёмка материалов.
2. **Следующая проверка → №16**: OGE16-D01, seed 19, oge16-circles-3, угол 90°.
   Снимок заморожен. Это известный дефект трапеции; верный ответ 90 по сохранённому
   эталону **не делает карточку принятой**. Генератор этим PR не исправляется.
3. **Следующая проверка → Формулы**: №8 R09, `1280/(4·√(10))²`. Сравнить Rich/авто
   и PNG, подсказку/разбор. В авто может сработать штатный fallback. Неверный ответ,
   затем «Повтор ошибки» открывает тот же snapshot без случайного перебора.
4. **Следующая проверка → №20**: отправить собственное синтетическое фото ответом
   на условие; нажать «Имитировать результат», затем «Имитировать ошибку». В QA
   хранится только факт вложения, без file_id/скачивания. Оценка 1/2 фиксированная,
   обозначена имитацией; точность модели этим не проверяется.
5. **Выйти**: пройти обычные меню ученика, открыть №20 и приложить тестовое фото
   обычным Reply. Реальный код привязки/удаления фото работает, «Проверить решение»
   использует безопасную заглушку без зачёта и бюджетных записей. Через меню команд
   Telegram «Проверки» вернуться к точным карточкам; команды запоминать не нужно.

Для других случаев: «По номеру / типу» → номер → сюжет/семейство/карточка.
№1–5 выбираются по сюжету и позиции. №6–18 принимают точный seed + версию;
№19 зависит также от истории/фазы, поэтому seed+version не обещает восстановления:
используйте сохранённый snapshot. Каталог №20–25 содержит reviewed-версии банка,
а не случайную задачу подтипа. Своя история №1–19 открывается кнопкой; последние
12 QA-снимков доступны по короткому ID, последний также кнопкой без копирования.
История №20–25 с вложениями остаётся в обычном «Прогрессе» staging. Чужих попыток
QA не открывает; разрешение на доступ к чужой истории не вводится.

## Покрытие и границы

| Проверка | Реализация / свидетельство |
|---|---|
| Владелец, private chat, команда, callback, Widget | Общий gate до claim/read; отрицательные тесты |
| Exact fixture / seed / версия / ID | Frozen JSON с digest; roundtrip; unsupported fail closed |
| Старые кнопки / Reply / дубликат / рестарт | Revision + message ID, PG advisory lock; свежий repo/dispatcher |
| Изоляция QA | Сравнение **всех public-таблиц** до/после; они побитово эквивалентны в JSON |
| Обычный ученик | Прежний dispatcher, реальная выдача №6, возврат того же problem ID |
| Фото | QA факт вложения; обычный collect на синтетике + stub; нет getFile/model/grades/budget |
| Rich → PNG / неизвестный исход доставки | Штатный presentation; явный отказ / timeout в transport tests |
| PNG результата → plain | Штатный `text_on_photo_rejection`; отдельная регрессия stub |
| Математика | Генераторы, политики, oracle и семейные флаги не менялись |

Автотесты используют TelegramSession с реальными aiogram payloads. Это **не** запись
живого Telegram и не проверка iPhone/Android. Бот и сервис не provisioned, поэтому
скриншотов телефона нет. Исходный мобильный дефект остаётся открытым до настоящего smoke.
QA — проверка одной карточки через общий replay. Полную последовательность обычной
тренировки, Mix, прогресс и ученические кнопки проверять в отдельном режиме ученика.

Сохранённый historical snapshot не становится качественным от успешного answer-check.
Режим вообще не выдаёт зелёную «карточка принята»: он показывает только совпадение
с эталоном. №16 и STOVE отдельно помечены известными ограничениями.

## Порядок интеграции с #106

База этой ветки — main `50b192e88686a3ea54a56d28197e275b7f6f2ca8`.
Ветка #106 не изменена, её модуль материалов не скопирован. Сначала интегрировать
проверенный #106, затем обновить этот PR от main, сохранив новый optional `controls`
в `error_replay._render` вместе с вызовами `scenario_materials` из #106. Возможны
текстовые конфликты в `CHANGELOG.md` и `error_replay.py`. Выполнить снова staging
suite и сценарные проверки #106 на **объединённом SHA**. Замороженный STOVE snapshot
остаётся прежним; общий renderer автоматически получает исправление #106.

PR — Draft, не разрешение на merge/deploy. Для фактического запуска пока требуются
действия владельца 1–7 выше, а затем мобильная приёмка выбранного кандидата.
