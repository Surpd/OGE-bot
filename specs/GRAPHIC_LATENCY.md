# Задержка выдачи графических задач

## Локальные измерения

Медиана трёх свежих выдач для каждого сценария. Windows, Python 3.12,
PostgreSQL 17.11 на localhost, настоящий aiogram Dispatcher и синтетический
Telegram transport. База сравнения — `b90fd21`. Для обоих запусков использован
seed планировщика 3: `OGE07-N04`, `OGE11-F03`, `OGE13-S02`. Время выдачи
измеряется от callback выбора номера до завершения обработки, включая
сохранение ID условия. Тестовый транспорт возвращает сообщение сразу, поэтому
его время не отражает загрузку изображения по сети и появление на устройстве.

| Сценарий | Выдача, мс до → после | Транзакция выдачи, мс до → после | Тестовый вызов отправки, мс до → после |
|---|---:|---:|---:|
| №7, график и Rich Message | 190,94 → 37,59 | 22,97 → 2,60 | 0,10 → 0,08 |
| №11, графики и Rich Message | 5 954,09 → 220,65 | 25,31 → 24,09 | 0,09 → 0,10 |
| №13, система и графические варианты в Rich Message | 212,48 → 86,61 | 2,92 → 1,78 | 0,10 → 0,08 |
| №13, принудительный PNG формул и вариантов | 333,56 → 213,94 | 2,71 → 1,89 | 0,12 → 0,10 |

## Профиль этапов

Отдельный инструментированный прогон тех же callbacks. Подбор включает
генерацию, а время рендера и проверок может входить в подбор. Поэтому колонки
пересекаются и их нельзя складывать. Это отдельная серия, её абсолютные времена
чувствительны к загрузке локальной машины и прогреву библиотек.

| Сценарий | Подбор с генерацией, мс до → после | Рендер диаграмм, мс до → после | Проверки, мс до → после | Компоновка формул в PNG, мс до → после |
|---|---:|---:|---:|---:|
| №7 N04, Rich | 122,93 → 8,05 | 119,82 → 7,82 | 29,82 → 20,85 | — |
| №11 F03, Rich | 3 060,25 → 196,21 | 1 439,14 → 135,30 | 1 627,26 → 60,54 | — |
| №13 S02, Rich | 61,92 → 0,43 | 489,82 → 72,09 | 0,98 → 0,25 | — |
| №13 S02, «Картинкой» | 103,87 → 0,44 | 791,12 → 67,16 | 0,99 → 0,26 | 957,30 → 99,83 |

Компоновщик формул не изменялся. Разница его времени между сериями отражает
условия замера, поэтому выигрыш ему не приписывается. Колонка «Проверки» включает
валидатор снимка №7, oracle №11 и проверки варианта/снимка №13.

В отдельном замере с seed 70000 планировщики материализовали 6 → 1
графический кандидат №7 (только N01), 32 → 1 кандидата №11 и 54 → 1
кандидата №13. В №11 объём подготовленных base64-данных сократился примерно
с 491 тыс. до 15–16 тыс. символов за вызов. Для одной задачи №11 отдельно
измерены генерация с PNG и обязательным oracle (медиана 75 мс) и контрольный
повтор oracle (27 мс) на текущем коде. Повтор не входит в путь свежей выдачи.
Для изолированного профиля нужен локальный тестовый `DATABASE_URL`:
`uv run python -m scripts.benchmark_graphic_latency --repeats 3 --seed 70000`.

## Что изменилось

- Выдача №7, №11 и №13 передаёт репозиторию первый кандидат, прошедший
  существующий фильтр недавних fingerprints. При повторе планировщик продолжает
  поиск в прежнем ограниченном бюджете. Транзакция заново проверяет актуальность
  перехода и fingerprint. Рендер не выполняется внутри транзакции.
- №11 раньше готовил до 32 графических кандидатов, повторно запускал oracle для
  каждого принятого кандидата и ещё раз проверял растр при выдаче. Свежая задача
  проходит независимую проверку растра при генерации, проверку семантики и хэша
  при чтении снимка. Обычное восстановление из базы сохраняет строгую проверку.
- №7 сверяет сохранённый рисунок с независимо проверяемой геометрией и точной
  моделью по seed. Для сверки используется исходный PNG без повторного рендера.
- №13 проверяет сохранённые варианты один раз на пути PNG. Растеризация длинных
  горизонтальных штрихов записывает целые ряды пикселей. PNG контрольных вариантов
  Q01 с seed 0–2 побайтово совпали с исходным рендерером.
- Режим «Картинкой» по-прежнему строит общий лист формул и рисунка. Автоматический
  режим отправляет исходный рисунок вместе с формулами в Rich Message. Резервный
  набор формул выполняется при штатном отказе Rich API или по явному выбору ученика.

Живой Telegram API, клиент и Render не участвовали в измерении. Сетевой вклад
и время холодного запуска остаются вне приведённых цифр.
