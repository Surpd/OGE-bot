# Представление математики в Telegram v1

Общий слой `app/bot/presentation.py` форматирует условие, подсказки, разбор и
правильный ответ при отправке. Снимок задачи, answer policy, математическая модель,
oracle и сохранённые шаги не изменяются. Технические сведения о происхождении
задачи остаются в metadata; ученический экран не содержит технического дисклеймера.
Предупреждение о том, что просмотр разбора закрывает самостоятельный зачёт,
сохраняется: это правило тренировки, а не технический дисклеймер.

## Проверенные возможности и выбранный транспорт

Проверено по официальной документации 2 ноября 2026:

- [Telegram Bot API: обычное форматирование](https://core.telegram.org/bots/api#formatting-options)
  поддерживает HTML в `sendMessage` и подписи `sendPhoto`, включая жирный текст.
  Данные, содержащие `<`, `>` и `&`, должны экранироваться.
- [Telegram Bot API: Rich Messages](https://core.telegram.org/bots/api#rich-messages)
  содержит отдельный `sendRichMessage`, LaTeX-формулы `tg-math` / `tg-math-block`
  и математические блоки. Это отдельный транспорт, а не дополнительный тег
  обычного `sendMessage(parse_mode="HTML")`.
- Проект закреплён на `aiogram==3.22.0`.
  [Документация этого релиза](https://docs.aiogram.dev/en/v3.22.0/api/enums/parse_mode.html)
  содержит обычные HTML/Markdown parse modes. Его опубликованный набор API
  предшествует Rich Messages 2026 года. Проверка установленной библиотеки также
  подтвердила: `aiogram.methods.SendRichMessage` и `aiogram.types.InputRichMessage`
  отсутствуют.

В v1 используется совместимый путь: обычные сообщения/подписи с явным HTML,
жирные заголовки и экранированный Unicode-текст формул. Новые Rich API не
вызываются; зависимости ради форматирования не обновляются. Это явный fallback
для неподдерживаемого установленной библиотекой LaTeX-транспорта: Unicode-формулы
остаются читаемым текстом с обычным HTML, без ложного обещания LaTeX-рендеринга. Существующие рисунки
№7, №11 и №13 остаются отдельными изображениями. LaTeX-исходники, `<sup>`, `<sub>`
и rich math tags не передаются как неподдерживаемая разметка обычного сообщения.

## Правила вывода

1. Заголовок задания, «Подсказка», «Разбор» и «Ответ» выделены жирным.
2. Между смысловыми блоками сохраняются пустые строки. Текст переносится клиентом
   по ширине экрана; широкие таблицы и фиксированные code blocks не используются.
3. Знаки сравнения, корни, дроби, степени, индексы и десятичная запятая остаются
   ровно такими, какими их создала проверенная математическая модель. Слой вывода
   не угадывает смысл `^`, `/`, скобок или минуса и не пересчитывает выражения.
4. Произвольная строка из snapshot не интерпретируется как HTML. Экранирование
   выполняется один раз на границе отправки, включая подписи изображений.
5. Идентификатор сообщения, клавиатура, состояние и зачёт не меняются форматтером.

## Контрольные примеры

| Представление | Контрольный текст |
|---|---|
| Дроби и отрицательные числа | `(−3/4 + 1/2) : 0,5` |
| Неравенство | `−2 < x ≤ 3` |
| Корень | `√(49) = 7` |
| Индексы и прогрессия | `aₙ = a₁ + (n − 1)d` |
| Квадратное уравнение | `x² − 5x + 6 = 0` |
| Формула | `E = mv²/2` |
| Вероятность | `P(A) = 3/10` |
| Линейная функция | `y = kx + b` |
| Соответствие | `А → 1; Б → 2; В → 3` |
| Текстовая степень | `2^(-3) = 1/8` |
| Экранирование | `<script>& 1 > 0` выводится буквальным текстом |

`tests/test_math_presentation.py` проверяет сохранение этих выражений, экранирование,
заголовки и одинаковый режим отправки текста/подписи. Эти проверки подтверждают
payload, а не визуальную отрисовку в реальном мобильном клиенте. Проверка реального
Telegram-клиента в рамках этого этапа не выполнялась; заявлять её пройденной нельзя.


## Явно типизированные математические фрагменты

`app/bot/math_fragments.py` задаёт независимый неизменяемый протокол `MathFragment`:
`unicode()` — совместимый текст; `latex()` — отдельный экспорт исходника LaTeX.
Есть узлы `MathToken`, `Fraction`, `Power`, `Root`, `Operation`, `Comparison`,
`System`, `Interval` и `Progression`. `send_text` и `send_photo` принимают как
обычную строку, так и явно созданный фрагмент, затем экранируют его Unicode-вывод.
LaTeX-экспорт транспортом не отправляется.

Узлы конструирует только вызывающий код, которому известна структура выражения.
Существующие проверенные snapshots по-прежнему показывают исходные строки:
они не разбираются регулярными выражениями и не преобразуются в новую модель.
`MathToken` сохраняет каждый исходный символ и экранирует команды при LaTeX-экспорте.
Структурные узлы выполняют только явно запрошенное оформление, без вычислений:
например, `Power` показывает заданный целый показатель верхними Unicode-цифрами.

| Явная структура | Unicode fallback |
|---|---|
| Дробь с дробью в знаменателе | `(−3,5)/((1)/(2))` |
| Степень отрицательного основания | `(−3)²` |
| Степень степени | `((x)²)³` |
| Дробный показатель | `(x + 1)^((1)/(2))` |
| Кубический корень дроби | `³√((8)/(27))` |
| Неизвестный индекс корня | `√[n](x)` |
| Система | `{ x > −2` и следующей строкой `x ≤ 3` |
| Полуоткрытый интервал | `(−2; 3]` |
| Арифметическая прогрессия | `aₙ = (1,5) + ((n) − 1) × (−2)` |

Операнды дроби, степени и арифметических операций заключаются в скобки,
чтобы вложенность и отрицательное основание нельзя было прочитать иначе.
Дробь через `/` остаётся безопасным fallback: горизонтальная дробная черта и
нативный LaTeX не обещаются. Неизвестные показатели используют явный `^(...)`.
Индекс прогрессии, отличный от `n`, обозначается как `a[индекс]`; он не заменяется
неверной фиксированной меткой `aₙ`. Интервальные границы и знаки сравнения задаются
явно, без вычисления или исправления математического смысла.

`tests/test_math_fragments.py` проверяет вложенные приоритеты, отрицательные
операнды, границы интервалов, точные literal tokens, отказ от неизвестных
операторов, LaTeX-экспорт и совместимую отправку. Ни Unicode fallback, ни
экспорт LaTeX не проходили визуальную приёмку в реальном Telegram-клиенте.
