# Автоматическая система качества — обязательные gate'ы

**Заказчик не проверяет тысячи задач вручную.** Все массовые проверки выполняют Codex, тестовый раннер и CI. Однако математические автотесты не являются абсолютным доказательством того, что условие похоже на ОГЭ: соответствие проверять по конкретным официальным/каталожным образцам; сомнительные подтипы остаются выключенными.

Для №10 применяются `atlas/oge10_reference_structures.json`,
`scripts/oge10_quality_report.py` и `reports/oge10-quality.json`. Счёт уникальности
основан на fingerprints параметров конструкции; замена только сюжета или числового клона
не подтверждает новый тип. Отчёт отдельно показывает точность/длину ответов, диапазоны
видимых чисел, знаменатели, операции и повторные fingerprints. Источников пока мало,
поэтому распределения частоты семейств указаны как предварительные.

## Уровень 0. Доказан экзаменационный формат
- Подтип связан с ID/URL существующего образца и номером/годом; текст источника не копируется в продакшен.
- Есть описанная математическая операция, целевая величина, допустимые контексты, формат ответов и уровни сложности.
- Подтверждён не только общий раздел, но и конкретная структура; иначе `research_only`.

## Уровень 1. Конструкция и rendering
- Условия представлены структурно (`MathAST`, `ScenarioWorld`, `GeometryModel`), а не собираются неуправляемой строковой подстановкой.
- Детерминизм `family + seed + version`, проверка границ и допустимых форматов.
- Рендерные формулы, знаки, скобки, единицы, варианты ответа совпадают с математической моделью.

## Уровень 2. Независимые оракулы
- Генератор не проверяет себя собственной формулой. Для дробей второй AST-парсер/интерпретатор; для уравнений независимый solver и подстановка; для прогрессий цикл и формула; для вероятностей перечисление исходов; для графиков координатная верификация; для геометрии независимая система координат/формула площади.
- Все параметры конечны и допустимы. Нет делений на 0, лишних корней, неверных округлений.
- Если выбор из вариантов — варианты различны и ровно одно/нужное количество являются правильными.

## Уровень 3. Массовые проверки
- Используются три уровня: быстрая разработка — 30–50 задач на семейство; основная — 200–300 задач на семейство с независимым oracle, ограничениями и отчётом; приёмка обычно требует не менее 200 уникальных валидных вариантов за ограниченный бюджет (до 1 200 попыток). Для подтверждённых типов с конечной меньшей ёмкостью возможно документированное исключение после проверки исходных случаев и отображённой структуры; тип остаётся выключенным, пока отдельно не проверены повторное использование, очередь и безопасный переход к другим типам. Очень большие стресс-прогоны необязательны и выполняются только при необходимости.
- Runtime production path повторно проверяет ручные пределы каждого кандидата. Превышение пределов запускает ограниченное повторное построение, а исчерпание попыток приводит к пропуску этого типа для текущей выдачи.
- При проверке ответы разрешаются по `family_id`, `answer_policy_id` и `answer_policy_version` из снимка выданной задачи.
- Полные регрессионные тесты и фиксированные граничные случаи выполняются независимо от объёма случайной выборки.
- Тесты property-based + фиксированные граничные случаи (отрицательные, 0, равные границы, перестановка вариантов, целый/дробный ответ, смена знака при делении неравенства).
- На каждый найденный баг создавать воспроизводимый fixture c seed и версией. Не решать ошибку только повторной генерацией.
- **Тесты старого бота**: ложный ответ дроби №6, двойной вариант №7, неверная граница №13, вероятность «ближайшего такси» №10, рестарт сессии, повторный webhook.

## Уровень 4. Графика и UI
- Проверка полигонов, пересечений, меток, геометрических инвариантов, читаемости размеров и различимости линий в мобильном формате.
- Snapshot/render tests; автоматические crop/overlap проверки. По возможности визуальный аудит моделью как дополнительный, **не независимый математический oracle**.
- Блоки №1–5 проверяются целиком: все 5 вопросов относятся к одному миру и одной схеме.

## Уровень 5. Сервис / эксплуатация
- GitHub CI: линт, типизация, property tests, миграции на чистой БД, webhook contract tests.
- Одновременно 10–50 учеников, два одновременных ответа на один вопрос, retry Telegram update ID, рестарт контейнера во время сессии.
- Сложное состояние хранить транзакционно. Встроенное ограничение rate limiting.
- `family_status`: research_only → tested → enabled; на любой регрессионной ошибке enabled → disabled, а не «оставить как есть».

## Вывод в prod
- Нулевое число ошибок **в проверенной выборке**, а не гарантия математической безошибочности мира.
- Каждая ошибка от пользователя сохраняет problem_id, исходный snapshot, seed/version и переводит подозрительный экземпляр в карантин. Для заведомо неисправного генератора переключить весь family flag.
- Release запрещён при провале CI или при отсутствии исходных подтверждений; никаких фиктивных «100% покрыто».
