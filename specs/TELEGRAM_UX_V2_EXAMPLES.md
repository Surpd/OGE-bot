# Telegram UX 2.0: экраны, примеры и план перехода

Этот документ дополняет нормативный [контракт](TRAINING_UX_CONTRACT.md). Тексты ниже — целевые примеры. Все действия используют обычные Telegram messages, inline keyboards, callback queries и ответы сообщениями; HTML-карточек и Mini App нет. Формулировка условия, подсказки и решения берётся из сохранённого snapshot через общий presentation transport.

## Экранный каталог

Обозначения: **M** — главное меню; **N** — выбор номера; **S** — сюжет; **R** — режим; **Q** — условие/экран задачи; **P** — прогресс. Целевое поведение меню — редактировать актуальное бот-сообщение M/N/S/R/P и при невозможности редактирования отправлять замену с новым ID. В `main` навигационный adapter действительно редактирует некоторые меню и создаёт replacement при `TelegramBadRequest`; это не доказывает единый контракт всех экранов. В №1–5 `render_session()` обычно отправляет новое текстовое сообщение и сохраняет его как control/condition ID; оно редактирует текущее сообщение только если передан `edit_current=True` и ID совпал. Фото схемы отправляется отдельно. Поэтому обещание единого транспорта — целевой план, не описание существующего поведения.

Каждый callback обязан проверить владельца Telegram user ID, чат, `callback_query.message.message_id`, ожидаемый экран/сессию/задачу и одноразовый идентификатор ревизии клавиатуры. Для обычной тренировки проверяются problem ID, текущий prompt ID и navigation revision; для №1–5 — session ID, позиция, revision и `control_message_id`. Эти проверки являются требованием спецификации: фактические обработчики реализуют их неодинаково. Старый callback только получает короткий ответ «Это меню устарело. Откройте главное меню.» и не меняет состояние.

Как заниматься?`\n`Вся пятёрка`\n`Одно задание`\n`↩ К сюжетам` | «Вся пятёрка» предлагает неизменный комплект №1→№5. «Одно задание» открывает позиции №1…№5 и «Случайная позиция». Временная модель хранения: одна незавершённая сессия на user × story × mode; Full и single независимы. Начало другого режима не стирает сохранённую сессию этого режима. Редактировать R; сам выбор режима не обновляет last-used. |
| **5. Найденная сохранённая тренировка**; выбран обычный номер имеет сохранённый активный или terminal контекст. | `Сохранена практика: №10 · [тема].`\n`▶ Продолжить`\n`🆕 Начать заново`\n`↩ Назад к номерам` | Для свободной практики не вводить порядковый номер занятия. Продолжить восстанавливает активный snapshot либо по явному нажатию выдаёт следующую задачу после terminal результата. Начать заново требует подтверждения: terminal outcome сохраняется, активная задача остаётся выданной без нового outcome и не превращается в пропуск. Нажатие «Начать заново» в №1–5 также требует подтверждения. |
| **6. Активная обычная задача**; создана/возобновлена задача №6–14. | `№10 · Вероятность`\n`[текст условия]`\n`Напишите ответ в чат.`\n`💡 Подсказка`\n`📘 Разбор`\n`⏭ Пропустить`\n`↩ В меню` | Ответ отправляется обычным сообщением; актуальный Reply на условие тоже принимается. Следующая задача не требует повторного входа через меню. Q — новое сообщение при выдаче; при возврате разрешено показать восстановленное условие из snapshot. Сохранять problem ID/snapshot, policy version, attempts, hints, status, condition ID, control ID, last-used. |
| **7. Активная задача №1–5 с изображением**; сюжетное условие использует общую схему. | Бот посылает исходную схему/таблицу (caption `Данные задачи · Шины`), затем `Шины · Задание №3 из 5\n[условие]\nНапишите ответ в чат.`\n`💡 Подсказка`\n`📘 Разбор`\n`⏭ Пропустить`\n`📷 Схема / данные`\n`↩ В меню` | Фото и условие — обычные Telegram photo/text. Схема относится к сохранённому комплекту; продолжение не регенерирует её. Q и управляющий message ID хранятся отдельно. Состояние включает весь snapshot, позицию, attempts, hints, prompt/control IDs и revision. |
| **8. Первая ошибка**; формат допустим, ответ неверен, attempts=1. | `Пока неверно. Попробуйте ещё раз.` | Условие и кнопки остаются актуальны; попытка сохранена. Технические счётчики не показываются. Ответ на новое условие не открывается. Повтор того же Telegram message ID идемпотентен. |
| **9. Верное решение**; задача solved. | `✅ Верно! Ответ засчитан.`\n`➡ Следующее`\n`↩ В меню` | Результат фиксируется независимо от занятия. Следующее атомарно выдаёт ровно одну задачу; меню сохраняет курсор и историю. Старый callback/ответ не меняет новый problem ID. |
| **10. Вторая ошибка**; допустимая вторая ошибка. | `Попытки закончились.`\n`Правильный ответ: [ответ].`\n`[пошаговый разбор]`\n`➡ Следующее`\n`↩ В меню` | Фиксируется failed, результат хранится. Дальнейший ответ не принимается; следующее создаёт новую задачу. Не раскрывать внутренние counters сверх понятного факта об окончании попыток. |
| **11. Подсказка**; запрос для active задачи. | `Подсказка: [текст подсказки]` | Отдельное сообщение либо редактирование result-message, но не prompt. | **13. Пропуск**; нажата кнопка только на active задаче. | Для обычного номера: `Задание пропущено.` затем новое сообщение следующей задачи. Старые callback не оживают: новую клавиатуру привязать к актуальному message ID/revision. |
| **15. | **16. Прогресс**; нажата кнопка главного меню. | `Мой прогресс`\n`Решено: X`\n`Верно с первой попытки: X`\n`Верно со второй попытки: X`\n`Пропущено: X`\n`Разборов просмотрено: X`\n`↩ В меню` | Использовать существующую семантику агрегатов: correct/attempts/hints/solutions/skips не смешивать. Не раскрывать технические ID/версии. Редактировать P или послать новое; не менять активную тренировку. |

### Особые случаи и открытые проектные решения

- Если сохранены занятия разных номеров и типов, «Продолжить» выбирает последнее фактически открытое/возобновлённое или использованное. Выбор номера/сюжета сам по себе last-used не меняет. Общий last-used между обычными номерами и №1–5 хранится в PostgreSQL.
- Для №1–5 временная модель по PR #33: не более одной незавершённой сессии для сочетания пользователя, сюжета и режима; Full и single сохраняются независимо. Не вводить несколько комплектов на одно такое сочетание. Вторичный список допустим только при реальной необходимости и не становится обязательным разделом главного меню.
- Если открыт terminal результат обычной задачи, «Продолжить» остаётся доступно, когда следующий шаг возможен. Только явное нажатие выдаёт следующее задание; предыдущий outcome не пересчитывается. Открытие меню/главного экрана не создаёт задачу и не меняет last-used.
- Для связанной пятёрки досрочная остановка фиксирует только уже выданные результаты. Невыданные вопросы не создают строк outcome и не входят в число ошибок/пропусков. Отдельный итог досрочной остановки отличается от штатного результата после вопроса №5.
- Настройки сейчас: вид формул (`auto`/PNG). Отдельный экран «Настройки» может быть оболочкой над имеющимся выбором. Не добавлять цель/напоминания/сложность без продуктового решения.
- Для обычной практики после `solved`, `failed` или `solution_viewed` выдать «➡ Следующее» и держать компактное продолжаемое состояние на номер, а не накапливать отдельные сессии бесконечно.

## Статус реализации

| Возможность | Текущее состояние |
|---|---|
| Главное меню и единый last-used | Main уже содержит четыре пункта, условное глобальное «Продолжить» и PostgreSQL-указатель last-used из PR #37. Terminal-задача свободной практики продвигается только явным нажатием. |
| Найденная свободная практика | Этот PR добавляет при повторном выборе №6–14 экран с «Продолжить» и подтверждаемым «Начать заново». Невыполненная активная задача не становится пропуском; завершённые outcomes и история остаются. |
| №1–5 | Main уже содержит шесть сюжетов, случайный сюжет, Full/Single, отдельные сессии по user × story × mode и сохранённый snapshot (PR #33). Этот PR добавляет подтверждение restart и итоги текущего комплекта; early finish не меняет невыданные позиции. ROUTE выключен. |
| Telegram transport | Меню навигации редактирует актуальное сообщение и отправляет замену при отказе Telegram. `render_session()` №1–5 обычно отправляет отдельное сообщение условия/контролов; фото схемы отправляется отдельно. Это реальное текущее поведение, а не общее обещание редактирования всех экранов. |
| Прогресс и настройки | Используются существующие агрегаты и вид формул (`auto`/PNG). Новых настроек и статистических показателей этот UX-этап не добавляет. |
| Короткий режим №6–14 | Не реализован и остаётся отдельным продуктовым предложением. |

Любые изменения сохраняют AnswerPolicy, snapshot, исходы, две попытки, отдельный учёт подсказок/разбора/пропуска, атомарную выдачу и проверки stale callbacks/Reply. Генераторы, миграции и инфраструктура для этого интерфейсного этапа не меняются.
