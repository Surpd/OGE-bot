# Контракт UX тренировок OGE Trainer

**Статус:** нормативный. Этот документ — единый источник правил Telegram-тренировок. Он обязателен для №1–19, включая существующие №6, №9 и №10. При расхождении локального обработчика с контрактом исправляется обработчик или добавляется согласованное исключение; молчаливое расхождение запрещено.

## 1. Модель задачи

Состояние относится к текущей задаче внутри сохранённой тренировки:

| Состояние | Значение |
|---|---|
| `active` | Принимает ответы. Счётчик попыток равен 0 или 1. |
| `solved` | Верный самостоятельный ответ; результат окончателен. |
| `failed` | Две допустимые неверные попытки; задача завершена. |
| `solution_viewed` | Ученик запросил полный разбор; самостоятельный зачёт закрыт. |
| `skipped` | Outcome пропуска. Фиксируется атомарно при создании следующей задачи; отдельного активного экрана без задачи не образует. |

`active`, `solved`, `failed` и `solution_viewed` — состояния сессии. `skipped` — терминальный outcome выданной задачи, хранимый в истории. После пропуска той же транзакцией становится активной следующая задача.

## 2. Разрешённые переходы

| Исходное состояние | Событие | Новое состояние/outcome | Эффект |
|---|---|---|---|
| `active`, попыток 0 | Валидный неверный ответ | `active`, попыток 1 | Записать попытку; не показывать ответ. |
| `active`, попыток 0 или 1 | Валидный верный ответ | `solved` | Записать единственную попытку; завершить задачу. |
| `active`, попыток 1 | Валидный неверный ответ | `failed` | Записать вторую попытку; показать ответ и разбор. |
| `active` | Подсказка | `active` | Увеличить число использованных подсказок; попытки не менять. |
| `active` | Полный разбор | `solution_viewed` | Записать просмотр; самостоятельный зачёт закрыть. |
| `active` | «Пропустить» | `skipped` → новая `active` | Учитывать пропуск отдельно; выдать ровно одну новую задачу. |
| `solved`, `failed`, `solution_viewed` | «Следующее» | Новая `active` | Создать ровно одну следующую задачу; старый outcome не менять. |
| Любое состояние | «В меню» | Состояние задачи сохраняется | Приостановить экран ввода; задачу и счётчики не менять. |
| Завершённое состояние | Ответ/подсказка/разбор/пропуск | Без изменения | Объяснить, что задача завершена; доступно «Следующее». |

Любой переход, не перечисленный выше, запрещён. В частности, обычное «Следующее» не превращает `active` в `skipped`, а просмотр разбора нельзя преобразовать в `solved`.

## 3. Кнопки и экраны

| Кнопка | `active` | `solved` / `failed` / `solution_viewed` |
|---|---|---|
| «Подсказка» | Выдать очередную доступную подсказку, не менять попытки. | Отклонить как устаревшее действие. |
| «Разбор» | Показать пошаговое решение, зафиксировать `solution_viewed`. | Повторный запрос не меняет outcome и не начисляет самостоятельное решение. |
| «Пропустить» | Зафиксировать `skipped` и выдать одну новую задачу. | Отклонить; завершённую задачу повторно не пропускать. |
| «Следующее» | Отклонить; задача остаётся активной, пропуск не начисляется. | Выдать одну новую задачу. |
| «В меню» | Приостановить тренировочный экран, сохранить задачу. | Приостановить экран, сохранив outcome и доступность продолжения. |

Во время активной задачи показываются подсказка, разбор, пропуск и меню. После её завершения показываются только «Следующее» и «В меню». Общие reply-клавиатуры меню и статистики не являются кнопками завершения задачи.

## 4. Ответы и Telegram-сообщения

1. Числовой ответ можно отправить обычным сообщением в чат. Telegram Reply не обязателен.
2. Reply на актуальное сообщение с условием также принимается. Reply на другое или устаревшее условие отклоняется без учёта попытки.
3. Тренировка хранит отдельно ID сообщения условия и ID актуальной управляющей клавиатуры. Обновление клавиатуры после ответа не меняет ID условия.
4. Сообщение ответа должно быть новее сообщения условия. Позднее доставленное старое сообщение не может ответить на новую задачу.
5. До записи ответа обработчик проверяет экран, статус, problem ID и соответствие Reply текущему условию. Репозиторий повторяет критические проверки под блокировкой/транзакцией.
6. Telegram message ID используется для идемпотентности. Повторная доставка одного сообщения не создаёт второй попытки. Повторный callback привязан к исходному сообщению и problem ID и не двигает уже сменившуюся сессию.
7. Некорректный по синтаксису ответ объясняет требуемый формат, но не расходует попытку. Верный ответ не сообщается после первой допустимой ошибки.

Для числа общий текст первой неверной попытки: **«Пока неверно. Попробуйте ещё раз».** После второй неверной попытки бот сообщает, что попытки закончились, показывает правильный ответ и пошаговый разбор. Типовой отказ для устаревшего ответа: **«Ответ к предыдущему заданию не принят. Напишите ответ числом в чат».** Эти тексты можно дополнить названием/форматом ответа, но смысл и правила попыток остаются теми же.

Базовая инструкция для числового ответа: **«Напишите ответ числом в чат. Дробную часть можно отделять запятой или точкой».** Дополнительный пример допустим, только если он соответствует политике ответа конкретного семейства.

## 5. Сохранение и переключение тренировок

- Прогресс каждой тренировки хранится отдельно: текущая задача, attempts, hints, outcome и история.
- У пользователя одновременно могут быть сохранены несколько тренировок, но экран ввода активен только у одной. Состояние экрана хранится отдельно от существования сессии.
- `/start`, «В меню», статистика и рестарт процесса не удаляют и не завершают активную задачу. Текст вне экрана тренировки не засчитывается.
- «Продолжить» открывает сохранённую незавершённую задачу с прежним ID, попытками, подсказками и политикой ответа. Выбор последнего раздела не изменяет остальные сессии.
- Переход к другому номеру явный. Ответ не должен попадать в предыдущую/соседнюю тренировку.
- Завершённая задача остаётся в истории и статистике, но не возобновляется как активная. Следующая задача создаётся только явным переходом.

## 6. Статистика

- `issued` — число выданных задач; каждая задача учитывается один раз.
- `attempts` — число принятых по формату ответов, включая верные и неверные; синтаксически некорректный ввод и дубликат не учитываются.
- `correct` — число задач, завершённых верным самостоятельным ответом. Answer после просмотра полного разбора, после завершения или после пропуска не засчитывается.
- `skipped` — число задач, outcome которых завершён действием «Пропустить».
- `hints_used` — число выданных подсказок; показ отказа/повторной подсказки не учитывается.
- `solutions_viewed` — число задач, для которых полный разбор был успешно раскрыт; повторный просмотр одной задачи не создаёт новую запись.
- Первая/вторая попытка — позиция принятого ответа в рамках задачи; ошибки и просмотр решения не увеличивают `correct`.

Метрики и определения должны совпадать между №6, №9, №10, PostgreSQL и экраном статистики. Семейный формат ответа может добавить профильные показатели, но не менять эту семантику.

## 7. Форматы ответа и допустимые различия

Общие состояния, попытки, пауза, идемпотентность и outcome не зависят от математического типа. Способ ввода и текст инструкций могут различаться по семействам только по реальной природе ответа:

- **Число:** одно сообщение с числом; точность и разделитель соответствуют версионируемой AnswerPolicy.
- **Выбор варианта:** допустим callback-кнопкой или номером варианта сообщением; сохраняются идентификатор задачи, выбранная опция и Telegram update/message ID.
- **Последовательность цифр/код:** допускается одна последовательность в заданном формате; сохраняется порядок символов, ведущие нули не удаляются.
- **Количество/целое:** проверяется как целое требуемого знака и диапазона.
- **Графический/рисуночный ответ:** разрешён только при наличии однозначного проверяемого ввода; если Telegram не предоставляет такой ввод, задача должна предложить согласованный числовой/вариантный ответ либо оставаться выключенной.
- **Другой формат:** вводится только после описания в спецификации семейства и тестов. Он не может обходить защиту от старого сообщения, двойного зачёта или завершённой задачи.

## 8. Обязательные автоматические проверки

Все активные номера подключаются через общий параметризованный контрактный тестовый harness. Для нового номера добавляется только адаптер его запуска/ответа/состояния; общие сценарии не копируются. Адаптер не может отключать применимые проверки.

Минимум для каждого номера: обычный ответ без Reply; две попытки и синтаксически неверный текст; актуальный и устаревший Reply; next против skip; next на active без пропуска; сохранение и продолжение; подсказка/разбор; старый callback и двойное сообщение; лишний текст после завершения; независимые сессии номеров. Для всех переходов с блокировками, статистикой и сохранением обязательны PostgreSQL integration tests в CI на PostgreSQL 17. MemoryRepository проверяет UX, но не заменяет PostgreSQL.

## 9. Пользовательские сценарии

1. **Обычный ответ:** ученик открывает №10, отправляет число без Reply; первое неверное допустимое сообщение учитывается, ответ не раскрывается; правильный ответ второй попытки завершает задачу.
2. **Старое условие:** ученик открыл новую задачу и ответил Reply на прежнее условие; бот сообщает, что ответ устарел, attempts текущей задачи не меняется.
3. **Пауза и возврат:** ученик сделал одну ошибочную попытку, нажал «В меню», посмотрел прогресс и перезапустил бота; «Продолжить» возвращает тот же problem ID с одной попыткой.
4. **Next против skip:** «Следующее» на активном задании ничего не пропускает. «Пропустить» завершает его с outcome `skipped` и ровно один раз выдаёт новую задачу.
5. **Разбор:** ученик открыл решение и отправил показанный ответ; задача остаётся `solution_viewed`, `correct` не растёт; «Следующее» выдаёт новый вариант.
6. **Двойная доставка:** повтор того же message ID или callback на старом problem ID не создаёт повторную попытку, повторный skip или вторую активную задачу.

## 10. Порядок разработки нового номера

Обязательный чек-лист: **исследование источников → математический oracle → UX-контракт → тесты → PR → CI → релиз**. До реализации нового номера Codex читает этот контракт и применимые уроки из `specs/LESSONS_LEARNED.md`. Новый номер следует существующему интерфейсу и общему harness; он не переопределяет общие правила.

Отступление возможно только при объективной необходимости формата: оно документируется в спецификации номера, покрывается автоматическими проверками и согласуется до выпуска. Без этого генератор/поток не считается готовым.
