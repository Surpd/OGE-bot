# Независимая проверка механик и доставки событий

## Обнаруженные дефекты и исправления

1. Первоначальная реализация выбора пяти позиций сначала брала две просроченные проверки, затем снова брала просроченные навыки, заполняя свободные места. При 80 просроченных навыках возвращалось до пяти обязательных повторений. Исправлен фильтр заполнения. Автотест проверяет максимум двух проверок даже после перерыва в 500 дней. Чтобы сохранить привычную тренировку из пяти заданий, три оставшихся места можно занять обычными свежими задачами из разрешённого пула. Такое задание само по себе не создаёт дополнительные обязательные повторения. Если и там нечего предложить, показать фактическое число доступных заданий.
2. На первой версии списка последних событий три события могли происходить с разрывами в несколько лет. Два старых правильных ответа и один новый создавали статус предварительного освоения. В ядре введено окно в 45 дней для недавних наблюдений. Проверка с паузой в 370 дней проходит. **45 дней — параметр прототипа**, его педагогическая калибровка ещё предстоит.
3. Смена snapshot и семейства защищает от простого запоминания, но в заданиях с коротким списком ответов удачная серия возможна у ученика, который выбирает ответы случайно. Ниже измерен этот эффект. Добавлена отдельная серверная метка пригодности задания для проверки в SQLite-адаптере. Отсутствующая метка по умолчанию исключает наблюдение из прямой квалификации. Ответ и режим сохраняются для привычной статистики. Банк заданий для ОГЭ требует отдельной разметки до выпуска.

## Как часто удачное угадывание даёт знак освоения

Ученик с постоянной вероятностью угадать получает одно новое задание в день, 90 дней подряд. Задания чередуются между двумя семействами одного навыка. Он не учится. Сравнивались **одинаковые** псевдослучайные ответы (seeds 0–999) для трёх моделей. Таблица показывает число учеников из 1 000, хотя бы однажды получивших награду при подаче *всех* ответов как допустимых доказательств. Откат математического статуса не отзывает полученный знак.

|Вероятность угадать|Правила|Взвешенная оценка|BKT-подобная модель|
|---:|---:|---:|---:|
|0,05|0|0|0|
|1/3|49|2|170|
|1/2|541|67|849|

При нулевом счёте верхняя граница вероятности всё ещё около 0,3% (односторонняя оценка для 1 000 независимых прогонов). Отличия моделей в таблице зависят от заданных порогов. Вероятность 1/3 уместна только там, где действительно равновероятны три ответа. Сложность открытого задания, состав конкретного банка и стратегия реального ученика потребуют отдельной оценки.

**Решение для пилота.** Методист указывает, какие формы могут свидетельствовать о переносе навыка. Для навыка нужен запас таких задач с разными условиями. Узнавание утверждения, выбор из двух вариантов, уже показанный ответ и задачи с почти постоянным ответом полезны для практики. Изолированно они не подтверждают обобщение. Нельзя снимать это ограничение простым переключением «решать самостоятельно». В адаптере даже 90 из 90 правильных ответов на неразмеченные формы сохраняются в обычных результатах, а наград за подтверждение остаётся ноль. Набор доступных проверочных задач хранится на стороне продукта.

## Стоимость и границы технической проверки

Команда `python bench_cost.py` пересоздаёт local_cost.json. На Python 3.12.7 и SQLite 3.45.3 выбор очереди при 25/250/1 000 навыках занял 17,7/219,7/760,4 микросекунды по p95 среди 1 000 локальных вызовов. Алгоритм сортирует S навыков за O(S log S), затем проходит список фиксированное число раз. Время включает только Python и не включает получение данных, поиск/генерацию невиданной задачи или Telegram.

Выдача в локальном адаптере выполняет 5 SQL-инструкций, ответ — 6, включая управление транзакциями. Пустая база заняла 32 768 байт, после 400 новых выдач и 400 ответов — 94 208. Амортизированная разница 154 байта на пару в данной искусственной конфигурации с короткими ключами. Это измерение SQLite с учётом дискретного выделения страниц. Реальный рост PostgreSQL зависит от индексов, длины ключей, VACUUM/WAL и переиспользования действующих таблиц. В пилоте замерить p50/p95 от кнопки до карточки, запросы через инструментирование, индексы посредством EXPLAIN, объём relations до/после тестовой загрузки в тестовом PostgreSQL.

## Что требует проверки до запуска

- В адаптере SQLite одна пишущая транзакция на БД. PostgreSQL потребует тестов конкурентных update/workers на целевой схеме. Эксперимент не проверяет живые Telegram updates, дедуп по bot_id для нескольких экземпляров или гонку доставки сообщения после commit. При реальной выдаче необходимо повторно отправлять **тот же** назначенный слот при неудачной отправке. Видимость заданий в других режимах, сценариях и при просмотре истории нужно учитывать глобально для ученика.
- Тестовый адаптер хранит `raw_action` отдельно от evidence и сохраняет exam/training на слоте. Вышедший в отчёт какой-либо статус допускает просмотр происхождения событий. Внешнее угадывание, подсматривание и помощь сверстника по финальному числу не обнаруживаются. Маркировка «самостоятельно» означает «первый ответ без зарегистрированной помощи в боте».
- Разные seed и даже разные хеши JSON могут давать одинаковое условие или один и тот же шаблон ответа. При выпуске проверить идентификатор математического содержания без декоративных полей и отдельных seed. Независимость семейства лучше подтвердить парой переносимых форм, согласованной методистом. Два искусственно разделённых family_id не создают перенос автоматически.
- Критерий двух семейств исключает некоторые узкие навыки. Для них в первом пилоте оставить «нужна другая форма проверки» или предварительно разметить действительно разные типы представлений в одном семействе. Количество закрытых навыков должно сопровождаться числом навыков, для которых вообще была доступна аттестация.
- Симулятор наследует выбранные предпосылки об обучении/забывании. Пороговые модели полезны для проверки логики. Прогнозы мотивации, времени удержания, школьной отметки и коммерческой ценности из них не следуют.
