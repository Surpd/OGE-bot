## 1. Ровно два семейства; проверенные источники

### `OGE18-M01` — средняя линия треугольника

Первоисточник: https://math-oge.sdamgia.ru/problem?id=348480 ; печатный каталог с исходным изображением: https://math-oge.sdamgia.ru/pdf/035b7415a9ab2fc0cdd2de50a8ed201e.pdf , лист 1/6, первая задача. Другие исходные ID той же конструкции: `348868`, `349105`, `349244`, `349561`. В примере №348480 A и C лежат на горизонтальной линии решётки, `AC=8`, верхняя вершина B, правильный ответ `4`. На исходном рисунке **показан только треугольник** и клетки: средняя линия, середины и дополнительные построения НЕ проведены. В тексте спрашивают длину средней линии, параллельной AC.

Модель генерации (предлагаемое безопасное подмножество подтверждённого типа): целочисленные точки `A=(x0,y0)`, `C=(x0+b,y0)`, `B=(x0+t,y0+h)` в декартовой модели до поворота y при растеризации. `b∈{4,6,8,10,12,14}`, `1≤t≤b−1`, `3≤h≤11`. Детерминированные вариации b,t,h и допустимого свободного поля сетки; не считать перенос всей фигуры/зеркало новым математическим fingerprint. Треугольник невырожденный, `AC=b`; ответ `m=b/2` — положительное целое. При переполнении изображения сокращай допустимый диапазон/отказывайся от кандидата, **не** ужимай клетки неравномерно и не обрезай подписи.

Независимый oracle: построить середины `M=(A+B)/2`, `N=(B+C)/2` точными `Fraction`; проверить `|MN|=|AC|/2` через квадрат расстояния и коллинеарность/параллельность `MN ∥ AC`. Проверять AC по конечным координатам; не принимать без проверки значение `correct_answer` от генератора. Проверить все три вершины, что они на сетке, и что рисунок показывает именно исходную конфигурацию. На PNG НЕ рисовать M, N и саму среднюю линию: это не дано ученику.

### `OGE18-M02` — средняя линия трапеции

Первоисточник: https://math-oge.sdamgia.ru/problem?id=348638 ; исходное изображение проверено в PDF https://math-oge.sdamgia.ru/pdf/aaef55676f047381cb69d6ae75078c3e.pdf , лист 5/5, задача 18. У исходной трапеции основания 9 и 3 клетки, ответ `6`; сама средняя линия **не проведена**, подписей сторон и дополнительных линий нет. Другие источниковые ID этой конструкции: `349153`, `349448`, `349451`, `349928`.

Модель генерации: `A=(x0,y0)`, `D=(x0+L,y0)`, `B=(x0+s,y0+h)`, `C=(x0+s+u,y0+h)`; обход `A→B→C→D→A`. `L=6..12`, `u=2..L−2`, `s=1..L−u−1`, `h=3..8`, все значения целые. Это выпуклая невырожденная трапеция, верхнее основание короче нижнего, строго горизонтально и параллельно ему, ножки внутри границ рисунка. Ответ `m=(L+u)/2`; допускается целое или число, оканчивающееся на `,5`. Не рисуй среднюю линию, её точки, высоты, числа на основаниях или иной методический намёк — в подтверждённом прототипе ученик считывает основания по клеткам.

Независимый oracle: определить длины обоих оснований **по координатам**, отдельно найти середины `AB` и `CD` точными рациональными координатами, вывести расстояние между этими серединами; сравнить с `(L+u)/2` и с нормализованным ответом. Независимо проверить параллельность оснований, положительную площадь по shoelace и отсутствие самопересечений; отличать основания от боковых сторон.

**Не включай** другие семейства №18 (`A01–A06`, `D01–D07`, `H01`, `L01–L02`) или №15–17/19 в этом PR. В частности, `OGE18-A03` (площадь треугольника) отложен до дополнительной источниковой приёмки изображения. Запрещено копировать картинки, водяные знаки и длинные исходные формулировки из «РЕШУ ОГЭ»/ФИПИ. Новый PNG должен быть авторским алгоритмическим чертежом той же математической структуры.

## 2. Генерация, версии, snapshot, ответ

- Номер задания в боте — **18**, не отдельный тип тренировки. Family IDs точно `OGE18-M01`, `OGE18-M02`. Используй seed-генерацию с локальным `random.Random(seed)`, без global random/random в отрисовке. Семейство + seed + версии генератора и рендера воспроизводят всё содержимое. Фиксированные seed 0, 1, 42, 2027, 90126 должны быть стабильными; отрицательные/граничные недопустимые значения валидируй явно.
- Snapshot **immutable** и самодостаточен: `problem_id`, `family_id`, `seed`, `generator_version`, `renderer_version`, источник(ID/URL) как provenance, точные целочисленные/рациональные точки, описание сетки, условие, `correct_answer` как canonical decimal string, versioned `answer_policy_id`, `answer_policy_version`, подсказки/разбор, fingerprint, PNG-содержимое (используя текущий способ для графического №11, например `png_base64`) и `image_sha256` (SHA-256 именно реально отправляемых байтов). Не хранить на диске/в Supabase отдельные PNG, если уже существующий snapshot-контракт это не требует. Предельный размер снимка/PNG, защита от corrupted bytes/unknown versions.
- Никакой регенерации другой задачи при `resume` или `retry`. Проверка ответа на выданную задачу использует policy/version из **её** snapshot. При восстановлении повторно валидировать SHA-256 и содержимое PNG, не строить альтернативную геометрию с новыми числами.
- Используй существующую числовую policy, если полностью подходит, или тонкий адаптер со строго точной арифметикой `Fraction/Decimal`. Принимать `6`, `6,5`, `6.5` в соответствии с правильным ожидаемым значением; `6,50` допустимо только если текущий numeric contract считает математически равным. Не принимать лишний текст, единицы, приближённый ответ, дробь не из поддержанного формата. Никаких ошибок из-за двоичного float.
- Ответы/решения порождаются из числовой модели; ещё один **независимый** oracle сверяет их из сохранённых координат, включая финально видимую подпись/условие; генератор не подтверждает сам себя своей служебной формулой.
- Подсказки по этапам, а не выдача численного ответа до самостоятельного решения. В режиме №18 текст задания не должен содержать длину AC/оснований, которой нет в оригинальном формальном условии: данные надо считывать с сетки.

## 3. PNG, читаемость и настоящая проверка картинки

- Существующие Pillow 12.3.0 и Matplotlib 3.11.2 уже доступны. Реализуй **прямой Pillow→PNG** без новой обязательной CairoSVG; SVG экспорт необязателен и не должен становиться runtime-зависимостью.
- Создавай исходный буфер в достаточно высоком разрешении, затем качественно масштабирую до контрольных 360, 390 и 430 px; проверяй сохранение квадратной формы клеток и **точного общего шага** по X/Y. В 360px ширины можно прочитать каждую вершину/сегмент/тонкую сетку на обычном телефоне.
- Поля не менее визуально безопасного запаса для букв, линии фигуры контрастны по отношению к серой сетке, точки/метки не выходят за границы. Для M01 A/B/C соответствуют правильным вершинам, не сливаются с линией. Для M02 базовая исходная постановка — **без названий вершин**; не добавляй их по привычке.
- Автоматически проверяй финальные пиксели, а не только `Image.verify()`: равномерность шага сетки; контрольные окрестности всех вершин/краёв и рисуемых сегментов; отсутствие срезанных областей, рассогласования между геометрическими и экранными координатами. Важная негативная проверка: на PNG нет лишней средней линии / середин / высоты / размеров оснований.
- Писать PNG всегда по проверенному immutable snapshot и повторно сравнивать байты/хеш в smoke тестах. Для source audit в отчёт прикрепить контакт-лист вариантов M01/M02 при 360px рядом с **ссылками** на подтверждённые образцы, без встраивания/массового копирования чужих оригиналов.
- Сложные случайные параметры не должны приводить к исчезновению меток или «плоским» неразличимым фигурам. При неудачной сцене ограниченно пересемплируй seed с фиксированным `attempt_index`, но фиксируй его в snapshot и fingerprint; при исчерпании — безопасный отказ, без ложной картинки.

## 4. Telegram, привычные режимы, хранение

- Подключи №18 в существующий реестр `TRAININGS`, номера, общий пользовательский сценарий «выбрать номер → получить задачу → ответить (до 2 попыток) → подсказка/разбор → следующее/пропуск → назад/пауза → продолжить». Переиспользуй текущие callback форматы и stale/revision защиту. При отрицательном ответе не выдавай новый seed, пока задача активна. Восстановление после рестарта сервера обязано работать.
- По возможности переиспользуй общее число/числовой training engine и existing image transport; если нужен узкий графический адаптер — ориентируйся на №11, но не копируй его целиком и не меняй чужие сценарии.
- Используй действующие модели сохранения `sessions`, `problems`, `attempts`, `users.current_state`, историю и подсказки. Если без минимальной миграции №18 не обойтись, сделай ОДНУ идемпотентную миграцию по принятому стилю, с PostgreSQL 17 тестом. Старые записи №1–14 не преобразовывай, не удаляй и не перезаписывай. Новые семейства должны попадать в существующие общие analytics автоматически либо оставаться невидимыми до включения, без правки PNG-прогресса.
- Проверить Rich Message с PNG/media, fallback на фото, сохранение message ID и callback, отсутствие двойной отправки при неоднозначном сетевом таймауте. Не нарушать альтернативный пользовательский режим «Вид формул → Картинкой».
- **Публичный флаг по умолчанию выключен:** `ENABLED_FAMILIES=()` или эквивалент существующей системы; тесты могут включать два семейства через явную зависимость/параметр. Нельзя показывать №18 ученикам до отдельного решения о релизе и живого Telegram smoke. Не скрывать отсутствующую поддержку за кнопкой, которая возвращает 500.

## 5. Тесты и quality gate

- Unit + deterministic / parametrized tests: одинаковые seed/version дают одинаковый snapshot, изображение и sha; разные значения математических параметров дают корректные ответы; золотые исходные oracle-cases: `OGE18-M01` №348480 → 4, `OGE18-M02` №348638 → 6. Отдельные fixed cases на ответ `,5`, зеркальную и смещённую сцену, слишком узкую/высокую фигуру, недопустимые координаты и старую версию renderer.
- Property-based в смысле **массовых генеративных/параметризованных проверок** (можно встроенными pytest/seed-loop; новый Hypothesis не нужен, если это лишняя зависимость) на корректность координат, площадей, параллельности, совпадения с независимыми oracle, парсинг ответа, отсутствие дубликатов в одной очереди, невозможность неверной картинки при формально правильном ответе.
- Негативные mutation cases: смена координаты вершины при старом ответе; перенос метки; исчезновение линии сетки; неравномерный шаг; добавленная средняя линия; неверный SHA; повреждённый snapshot; replay устаревшего callback; 2 одновременных ответа; duplicate webhook; restore после рестарта и after-version-upgrade. Все они должны детектироваться тестом/валидиатором, не просто создаваться.
- Быстрый smoke 50 seed на семейство. Основной отчёт: **минимум 300 сгенерированных кандидатов на семейство**, проверенных валидным oracle. Цель — ≥200 различных *содержательных fingerprints* на ≤1200 попыток, где fingerprint учитывает длины, существенные геометрические отношения и цель задачи, но не считает только перенос, цвет, зеркальную перестановку или подписи математической новизной. Если реальная ёмкость этих узких семейств не позволяет честно получить 200 содержательных вариантов, явно зафиксируй меньшую ёмкость и причину, соблюдай существующие правила `specs/QUALITY.md`, а семейство оставь выключенным. **Никаких фиктивных процентов покрытия.**
- Создай `scripts/oge18_quality_report.py` и `reports/oge18-quality.json` (или следуй сложившемуся формату), исходные контрольные PNG и **contact sheet минимум по 20 разных валидных вариантов на семейство**, включающий крупный исходный и телефонный вариант. PNG-превью сохраняются в `reports/previews/oge18/` или аналогичной новой папке, не в папках PNG-прогресса. Ручную визуальную проверку в отчёте не объявлять выполненной, если её не было. Добавить гарантии, что бинарные файлы не раздувают репозиторий (не коммитить сотни изображений; достаточно маленького reproducible набора).
- Тесты Telegram/DB для старта, следующего, двух попыток, подсказки/разбора, пропуска, перезапуска, resume, stale/repeat/race, правильных PNG bytes/message IDs, неактивного публичного флага. Старый полный suite должен не измениться по поведению.
- Запустить **`uv sync --frozen --all-extras`; `uv run ruff check .`; `uv run mypy app`; `uv run pytest -q --durations=10` с настоящим `DATABASE_URL` на PostgreSQL 17**. Используй существующий GitHub Actions `ci.yml`, который поднимает сервис PostgreSQL 17; CI на PR должен пройти. Не объявлять local полный PG QA пройденным, если базы в окружении нет: в таком случае выполнить доступное локально, а полноценный статус получить из GitHub Actions.
- Не отключай flaky-тесты, не делай `skip` для существующих тестов ради зелёного CI, не изменяй зависимости/lock без необходимости. Если обнаружен баг общего транспорта — маленький адресный фикс с отдельной регрессией; если проблема шире границ первого PR, документируй вместо большого рефакторинга.

## 6. Что положить в PR и когда считать задачу завершённой

Одно узкое изменение в области geometry18: source-mapping `OGE18-M01/M02`; математическая генерация, независимая геометрическая и проверка правильного ответа, Pillow PNG и pixel-audit, versioned snapshot, тонкая интеграция с существующей тренировкой, массовый отчёт, contact sheets, тесты и понятная документация. В PR description перечисли точно изменённые файлы и версии, source ID + URL и за что отвечают, параметры, ограничения, количественные итоги QA, количество уникальных fingerprint, известные HOLD/blockers, ссылку на Actions run, результаты проверки старых тренировок и остаточный риск по мобильному Telegram.

Обязательно **вернуть ссылку на один PR, commit SHA, статус CI и точный список выполненных и невыполненных проверок**. **Не merge, не deploy, не включать №18 публично**, не изменять прогресс. Если корректная интеграция слишком велика, уменьши число затронутых файлов/перенеси некритичный polish, но не жертвуй корректностью, oracle, PNG и тестами.
